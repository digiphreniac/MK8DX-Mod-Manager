# Mario Kart 8 Deluxe Mod Manager

A local desktop app for managing MK8DX romfs mods end to end, replacing the
old workflow of manually downloading archives, extracting them, editing
`active-mods.txt`, and hand-merging folders before copying to the SD card.

Given a character or a course, it can:

- Search/browse GameBanana for that character's or course's mods (or fetch
  a mod directly by link), right from the app.
- Download and extract the mod, auto-detecting its `romfs/` folder - and
  auto-fixing the most common ways a downloaded archive turns out to be
  packaged wrong (missing `romfs/` wrapper - including a pack that ships bare
  `Audio/` next to bare `Course/` + `MapObj/`, where all of them go into the one
  `romfs/` so the music isn't staged without its track - a pre-packaged Atmosphere SD-card
  tree - including the older `atmosphere/titles/` layout, with or without the
  title-id folder - a bare course-slot folder with no wrapper at all, loose item-model
  files with no folders around them, and a few others -
  see the comments above each `fix_*` function in `mod_manager.py`).
- Let you check off which downloaded mods should actually be merged, per
  character/course, and warn about real conflicts (two checked mods writing
  the same file with *different* content - byte-identical coincidences don't
  count) before you commit to anything.
- Stage the combined result into `../sd-card-staging/atmosphere/contents/<title id>/`,
  ready to copy onto the Switch SD card.

## Where things live

- `src/mod_manager.py` - backend (a pywebview JS-API bridge; almost all of the
  actual logic lives here)
- `src/ui/` - the frontend (plain HTML, CSS and JS; no build step) - see "Frontend file layout" below
- `src/voice_audio.py` / `voice_edit.py` / `voice_dsp.py` / `voice_api.py` - character voices. `voice_audio.py` reads a voice archive
  (`.bars`) and decodes its sounds so the app can play them; `voice_edit.py` rewrites an archive with some sounds swapped
  (and knows what each voice line is called); `voice_dsp.py` turns audio into the game's sound format; `voice_api.py` is the
  Api's side of it (the Custom voice mod, where the starting archive comes from) - see "Voice editing" below.
- `voice-edits.json` / `voice-custom/` - what you muted or replaced per character, and the audio you chose for the
  replaced lines (kept so a line can be encoded again if the archive it goes into changes). Both auto-generated.
- `src/game_files.py` - the app's own local copy of the base game's files (menu icons/text, every character's default
  voice) - see "Base game files" below.
- `game-files/original/` / `game-files/current/` / `game-files/manifest.json` - that copy. Auto-generated by the
  required Setup step; `original/` is never touched again after it's written, `current/` is what every other part of
  the app reads.
- `src/gamebanana_api.py` - the GameBanana API client
- `src/cup_icons.py` - reads the game's own Grand Prix medallions out of the app's copy of `menu.sarc` for Course Select -
  see "Course Select" below.
- `src/vehicle_icons.py` - the same for the game's own pictures of every vehicle part, for the Vehicles screen - see "Vehicle
  parts" below.
- `src/item_icons.py` - and for the game's own pictures of every item, for the Items screen - see "Items" below.
- `src/bntx_decode.py` - decodes a course mod's own `ym_CoursePict_*.bntx`
  select-screen thumbnail (a Switch BC7 or RGBA8 texture) to PNG, for the
  inline preview in Course Select - see its own docstring for exactly what
  it does and doesn't handle. Needs `Pillow` (see `requirements.txt`) for
  the actual BC7 decompression.
- `src/bntx_encode.py` / `_bntx_structs.py` - the write side: generates a new
  `ym_CoursePict_*.bntx` from a mod's own GameBanana screenshot when it
  doesn't bundle its own icon - see "Course-select icon preview &
  generation" below.
- `src/roster.json` - the full roster: every character and course (courses
  grouped into their 24 cups) plus every vehicle part (bodies, wheels,
  gliders - see "Vehicle parts" below) and every item (see "Items" below), used so every one shows up in the
  app even before anything's downloaded for it. Each course entry also
  carries its real internal `romfs/Course/<id>/` folder name (see below).
- `gamebanana-mods.json` / `mod-manager-state.json` - your tracked downloads
  and "Mods to merge" checkbox state (both auto-generated, no need to touch
  by hand)
- `mods/downloads/<category>/<item>/` - raw downloaded archives, one folder
  per character/course
- `mods/extracted/<category>/<item>/<mod name>/romfs/...` - what those
  archives unpack to (what `discover_mods()`/`find_mod_units()` scan). A mod
  is nested under its item's own folder rather than named `<item> - <mod
  name>`, so e.g. every Waluigi mod sits together under `extracted/
  characters/Waluigi/` instead of as separate flat `Waluigi - ...` folders -
  this happens automatically (see "Folder naming" below).
- `ui-icons/` - the combined character-select icon set and menu text: either
  files you built by hand (stays separate from the checklist) or the ones
  **menu icons & text** builds for you, automatically, as part of every commit
  (`ui-icons/romfs/UI/cmn/common.sarc`, `menu.sarc`, `UI/<locale>/message.sarc`
  - see "Menu icons & text" below). Always merged in.
- `ui-icons-backups/` - a timestamped copy of any file in `ui-icons/` that a
  build replaced or removed (never deleted automatically)
- `ui-setup-cache.json` - cache of the icons/text read out of your mods'
  archives (safe to delete; it just makes the next build faster)
- `excluded-files.json` - files each mod must NOT contribute to a commit (how
  clashes are settled, and per-file choices from a mod's "Files" button - **Edit included files** in a character mod's **...** menu) - see
  "Conflicts: leaving files out" below
- `src/name-labels.json` - shipped reference data: which numeric text entry of the game's
  `Common.msbt` holds each character's (48) and course's (96, both the short and the
  cup-line entry) name - the numbers are the same in every language and every mod. Lets
  a name be handled without opening any game file, and lets the app tell when a mod's
  own text file already renames a character (its entry no longer matches the game's
  name). Villager (Boy)/(Girl) aren't listed (two identical "Villager" entries).
- `ui-overrides.json` + `ui-overrides/*.png` - icons and names you supplied in
  a character/course popup's "Menu look" card - see "Menu look" below
- `look-reviews.json` - which characters' looks you have confirmed with "Looks right" (see "Checking a
  character's look" below)
- `part-icons/` - the user's own pictures for vehicle parts that are loose files (see "Vehicle parts: names and pictures in
  the menus"); the same idea, always merged in.
- `course-icons/` - app-generated course-select icons (see "Course-select
  icon preview & generation" below) - always merged in, same idea as
  `ui-icons/` but kept separate so generated files never mix with your own
  hand-curated icon work

For the day-to-day usage guide, see the app's own **Help** panel (top
right) - it covers the five-step flow, Menu Look, voice editing, conflicts,
the file-status glossary and known issues, and stays current with the UI
since it lives in the UI itself (`src/ui/html/help-modal.html`) rather than a separate doc.

## Frontend file layout

The UI is plain HTML, CSS and JavaScript under `src/ui/` - no build step, no bundler, no modules. pywebview serves that folder
over its built-in local HTTP server (which is why relative links and `fetch()` work), so everything the page loads must live
under `src/ui/`.

- `index.html` - the page frame only: the header, tabs, the main views, the footer, and one `<link>` per stylesheet.
- `html/*.html` - one file per modal / overlay (`help-modal`, `settings-modal`, `add-mod-modal`, `gb-browse-modal`,
  `gb-detail-modal`, `icon-gen-modal`, `guessed-names-modal`, `character-modal`, `setup-overlay`). `js/bootstrap.js` fetches
  them and adds them after the frame, in the order it lists them (the order is their stacking order).
- `css/*.css` - the styles, split along the old file's section comments. **Order matters**: later rules override earlier ones,
  so the `<link>` order in `index.html` is the cascade. Add a stylesheet after whatever it needs to override.
- `js/*.js` - the app. These are ordinary (non-module) scripts that share **one global scope**, run one after another in the
  order `SCRIPTS` lists in `js/bootstrap.js`: state and helpers first, then tiles, the character card, the views, add-a-mod,
  settings, the guided flow, and `main.js` (the `pywebviewready` handler that starts the app) near the end. Top-level code in a
  file may use anything an *earlier* file declared, but not a later one (a function declaration is only hoisted within its own
  file), so a new file goes where its dependencies are already loaded.

`bootstrap.js` also covers one timing trap: pywebview fires `pywebviewready` once, as soon as the page has loaded, which can be
before `main.js` has registered its listener now that the scripts load one by one. It notes the event and replays it once every
script is in.

Which file holds what, roughly: `tiles-and-review.js` (character/course tiles, the "have you checked the look" review),
`character-select-layout.js` (the docked card, hover name bar), `gamebanana.js` (the mod detail window and the GameBanana card), `refile.js` (a mod for something other than its card: the note, Undo, "Move to..."),
`gb-browse.js` (the Browse GameBanana window), `rich-text.js` (descriptions with links),
`voice.js` (playback, the voice editor, the "Use my own sound" tool, the card's Voice row), `character-card.js` (the card
itself and its Name / Icons walkthroughs), `help-and-icon-generator.js`, `views.js` (Full List, More, Course Select, tab switching), `vehicle-screen.js` (the Vehicles screen), `vehicle-card.js` (the vehicle card's "Right part" step), `item-screen.js` (the Items screen, its docked card and fit), `item-card.js` (the item card), `course-card.js` (the course card's Name and Icons steps), `add-mod.js`, `data-and-conflicts.js` (loading mods and settings, conflict cards),
`settings-panels.js` (master directory, UI setup card), `menu-icons-text.js` / `menu-look.js` (the base-file copy and the
Menu Look cards), `flow.js` (step bar, Commit, Copy to Switch), `setup-wizard.js`, `tooltips.js`.

## Browsing GameBanana: one window for every kind of mod

"Browse GameBanana" (`js/gb-browse.js`, markup in `html/gb-browse-modal.html`, styles in `css/gb-browse.css`) is the same window
whatever card opens it - a character, a course, a vehicle part, an item, or one of the plain categories. Only where the list
comes from differs (`fetchPage()`): `gb_browse` (a character's subcategory), `gb_browse_simple`, `gb_browse_vehicle`,
`gb_browse_item` - all sortable categories - or `gb_browse_course`, a search - and `gb_search` when the user has typed one.

- **The list loads as you scroll** (no pages). `checkFill()` asks for the next batch whenever the end of the list is within
  `GB_LOOKAHEAD` (500 px) of the window's bottom edge - after each batch, on scroll, on resize, and when the layout changes - so a
  tall window fills itself and a short one loads on demand, and a row is never left half-empty until the very end. Every backend
  browse call returns `{records, total, done, next_page}`; the window asks for `next_page` (a course search advances by three
  search pages per call), drops mods it already has (GameBanana repeats a few across pages in its Most Liked order), and ignores a
  reply that arrives after the sort changed or the window closed (`S.gen`).
- **Grid or list**: one set of tiles, with `.as-list` on the container switching to small pictures beside the text (plus the
  author and date). Under the "looks like it replaces X" filter, batches that add nothing stop the automatic loading after
  `GB_EMPTY_RUN_LIMIT` (2), because each batch costs a GameBanana request per mod.
- **Remembered**: the layout and the sort are settings (`gb_browse_view`, `gb_browse_sort` in `settings.json`, saved when the user
  changes them). Before any choice, vehicle parts and items start on Most Viewed, the rest on Most Liked. A course has no sort:
  GameBanana's search endpoint ignores every sort parameter (tried several spellings), so its results are always best match first
  and the sort box says so.
- **Courses** have no category per course, so they search by the base course name (`search_course_mods()`: three search pages at
  once, kept to the Course Edits / Course Retextures / Custom Race Courses subcategories - most results are something else).
  Each mod comes with a snippet of its description around the course's name and `mentions_course` (named in its title or
  description), shown as a badge like the "Replaces X" ones on vehicles and items; an "only mods that name this course" filter
  is there too, off by default. Descriptions are fetched through `_descriptions()` and cached (`_gb_desc_cache`), shared with the
  vehicle and item lists, which now show a snippet too.
- **Search** (the box in the window's header): searches all of Mario Kart 8 Deluxe through the same full-text search the course
  list uses (`gb_search(category, query, page)` -> `search_filtered()`), then keeps the kind of mod the card is for. The kind is
  read from the GameBanana category each result is filed in (`_search_kind()`: the vehicle-part and item category ids, the course
  subcategories, a subcategory named after a roster character, or a plain category) - so a search from a character's card lists
  character mods of *any* character (each tile says which one it is filed under; green when it is this card's own - the download
  moves it to the right card if its files say otherwise, see below), and one from a tire card lists any vehicle part, with the
  usual "Replaces / Mentions" badges read against the roster of the result's own section. Results are best match first (no sort),
  are shown with a snippet around the words searched for, and load as you scroll like everything else; a batch that has none of the
  kind wanted counts towards a pause after `GB_SEARCH_EMPTY_RUN_LIMIT` (4). Emptying the box (the x, or Esc - a second Esc closes
  the window) goes back to browsing with the remembered sort. A search with nothing found offers to search gamebanana.com itself.
  The card's paste field is the shortcut into it: a link or id is fetched as before (`looksLikeModRef()`), anything else opens this
  window already searching for it - the field's button changes from "Fetch" to "Search" as you type.
- **The More tab's categories** (`SIMPLE_MOD_CATEGORIES`, mirrored by `SIMPLE_CATEGORIES` in `state-and-helpers.js`): Mechanics, UI,
  Code patches (GameBanana's own category for exefs `.ips` mods), Modpacks and Battle courses (the Custom Battle Courses
  subcategory - the course roster has no cards for battle arenas, so those mods get one place of their own instead of showing up in
  a race course's search). Each is one fixed pseudo-item that browses, searches and adds links like any card. A modpack stays filed
  under Modpacks, but `get_pack_links()` lists it (with its "Pack" badge) on every character / course / part / item card it
  replaces - the same mechanism as any other pack. Adding one of these needs an entry in both lists and an `<option>` in
  `add-mod-modal.html`.
- **What a card's search keeps** (`_search_kind()`): its own kind; for characters, vehicle parts and items also GameBanana's
  Skins > Packs and Skins > Other/Misc (mods of those kinds that no single roster entry names); for Modpacks also Skins > Packs.
  Custom Lighting counts as a course kind (`COURSE_SEARCH_SUBCATEGORIES`). The search endpoint also returns WIPs, questions and
  requests, which `search_mods()` drops - none can be downloaded.
- **Tags**: a mod's own page gives tags as `{"_sTitle", "_sValue"}` objects (the list gives strings) - `tag_names()` turns both
  into "Title: Value" strings.
- **Links in descriptions**: `gamebanana_api.html_to_runs()` turns a description's HTML into runs (`{text}` / `{text, href}`;
  http(s) and GameBanana-relative links only, everything else is plain text) and the record keeps them as `description_runs`
  beside the plain `description` that the guessing uses. `renderRichText()` builds the text nodes and `<a class="gb-link">` itself
  (never markup from the mod); a click calls `open_external_url()`, which opens http(s) addresses only, and the tooltip shows where
  it goes. A mod saved before runs existed, or text with no link markup, still gets bare `https://...` addresses linked.

## Course Select: the game's Prix, sized to fit

The Courses tab shows the 24 Grand Prix as the game's own medallions on a board (like Character Select's), the selected
Prix's four courses under it, and a name plate along the bottom.

- **The medallions** come from the base game files (no mod needed): `menu.sarc` -> `mn_L_CupSlctBtn_00.szs` -> one 200x200
  `ym_CupIcon<Name>^h` texture per cup. They are 16-bit blue-green-red 5-6-5 with no alpha - a round medallion on a square
  backdrop - so `cup_icons.py` unpacks them, swaps red and blue, and cuts the circle. `Api.get_cup_icons()` returns
  `{cup name: PNG data URI}` (decoded once, about a second, and remembered until `menu.sarc` changes). The base game's
  cups are named after their emblem (Mushroom ... Thunder) or, for the four DLC-wave cups, `DLC02`..`DLC05`; the Booster
  Course Pass cups are `Charger00`..`Charger11`, in the pass's order - `cup_icons.CUP_TEXTURES` is that mapping, checked
  against the decoded pictures. Before Setup has copied the game's files there is no artwork, and the tiles keep the old
  gold-rimmed emoji look until there is.
- **The name plate** is Character Select's (same look): the selected Prix, or - after you click a course - that course
  with its Prix small and dim beside it; while the mouse is over a tile it shows that tile's cup or course instead, and
  goes back when the mouse leaves. Choosing another Prix (or clicking the selected one again) drops the course selection.
  Course tiles keep their yellow brackets while selected; the white hover frame works as on the character grid.
- **Two pages, nothing scrolls.** The 24 cups are on two pages - the game's 12 and the Booster Course Pass's 12 - with an
  arrow beside the board to turn between them and a small caption ("Mario Kart 8 Deluxe - 1 of 2"). A dot on the arrow says
  the page it leads to has modded courses. Selecting a cup on the other page (or jumping to a course from a conflict) turns
  to its page. `fitCourseScreen()` (`views.js`) sizes everything from the room there is: cups per row (`--cols`; it tries
  6, 4, 12 and 3), a cup (`--cup`) and a course tile (`--course-w`, 16:9 pictures), keeping the layout where the smaller of
  "cup size" and "course tile size", each against a comfortable reference, is biggest. It re-runs when the window resizes
  and whenever the tab is shown. A cup with no modded course is faded (like an untouched character); a bubble shows how many
  of its courses are modded. All of it is in `css/course-screen.css`, which comes last so it overrides the shared tile
  rules. (An earlier version showed all 24 at once, four rows of six, when the window was big enough; two pages at every
  size won out: bigger cups and course tiles, and one layout to reason about.)
- **The game's own course pictures.** A course tile with no picture from a mod shows the game's own course-select picture (from
  the base game copy - `Api.get_course_default_pictures()`, decoded like a mod's and cropped to the same visible window, under
  the same white name banner), faded like any untouched tile; a ticked mod that ships its own picture replaces it. Base-game
  courses are found by their internal id (`Gu_FirstCircuit`; Animal Crossing's four seasons share `Du_Animal`); the Booster
  Course Pass's 48 are `DLC01`..`DLC48` in the pass's order (their internal ids, `Cnsw_NN`, are in a different order - the
  mapping was checked against the pictures). The course card's Icons step shows the same picture when the mod brings none.

### The course card

Clicking a course opens the same kind of guided card as a character (`course-card.js`; the mods list, "Find a mod" /
"Add another mod" and conflicts are built by `openCharacterModal()` for both): a head with the course's (modded) name, its
Prix and a status chip, the mods in use with **Manage**, then two steps.

- **Name** - asked when something wants the course called other than the game's own name: the mod's own text, a name you
  typed, or a guess from the mod's name or folder (`get_course_look()` -> `name.suggestion`; you use it, change it, or keep
  the game's). Nothing to check otherwise.
- **Icons** - the course-select picture. A ticked mod that bundles its own `ym_CoursePict_*.bntx` needs no check; otherwise the
  game's own shows, or a picture you make from one of the mod's saved screenshots (the existing crop tool,
  `generate_course_icon()`), and you settle it once ("Keep the game's picture" / "Use this picture").

Each is confirmed for the SET of ticked mods and remembered in `look-reviews.json` (`course_names`, `course_icons`, next to the
characters' two records - `_ticked_by_course()`, `_mark_course()`, `confirm_course_name()`,
`mark_course_icon_reviewed()`); typing or clearing a name confirms the Name step. `get_course_tile_view()` gives the course
tiles their marker (amber = something needs a look, green = done - `refreshCourseReview()` / `applyCourseMarkers()` in
`views.js`, cached in `courseReview`).

**Unfinished courses count like unfinished characters.** A course with ticked mods is unfinished until its Name and Icons steps
are *explicitly* confirmed (where they apply - see above). They feed the same three things: the step bar's "N to finish", the
Next button's hint, and the prompt when leaving Choose mods ("2 characters and 1 course aren't finished" - `freshUnfinished()`,
`showUnfinishedGate()` in `tiles-and-review.js`). "Review them" is one guided pass over both kinds (`reviewQueue.items` are
`{kind, name}`): characters first, then courses; a course opens with its Prix and the course selected (`openCourseCard()`), the
bar on top says "Reviewing unfinished courses (or characters, or characters and courses) - 2 of 3", and finishing a card moves
on after a moment (`onItemFinished()`).

## Base game files: a required local copy

The app needs a few of the game's own files: the two icon archives, one `message.sarc` per language, and every
character's own default voice archives. It can't ship them itself (they're Nintendo's), so a required Setup step
(`game_files.py`) asks for the folder the user extracted from their own game and copies what it needs from it - not
the whole extraction, just `UI/cmn/common.sarc`, `UI/cmn/menu.sarc`, `UI/<locale>/message.sarc` for every locale
found, and `Audio/Driver/Driver_<slot>.bars` + `Audio/DriverMenu/MenuDriver_<slot>.bars` for every character in
`DRIVER_SLOTS`, plus every course's own select-screen picture (`UI/cmn/menu/ym_CoursePict_<id>_00^u.bntx`, about 105 files,
9 MB) and the 351 loose vehicle-part pictures that aren't inside `menu.sarc` (`UI/cmn/menu/tc_KP_*`, 38 MB - see "Vehicle parts"); both
kinds are optional: a dump without them, or a copy made before they were added, still counts as done. Real sizes measured: the
whole copy runs well under 300 MB, nowhere near a full RomFS dump.

**Adding the pictures to an older copy.** A copy made before the course pictures (or the vehicle pictures) were part of it has
no `course_pictures` (`vehicle_pictures_all`) in its manifest (a copy from when only 16 of the vehicle pictures were kept has `vehicle_pictures` but not `vehicle_pictures_all`, and gets the rest). The first time Course Select or the Vehicles screen asks for a
picture, `top_up_pictures()` fetches what is missing from the folder the copy was made from - if that still exists - into
BOTH `original/` and `current/` (adding files only; nothing already there is touched) and records the count, so each is
tried once. If the source folder is gone, the pictures come with the next "Update from a new dump" (Settings), and the
screens simply show their plain tiles meanwhile.

**Two copies**, both under `<master root>/game-files/`:
- `original/` - written once (`copy_both()`), never touched again except by "Update from a new dump" (which replaces
  it outright - no history of older game versions is kept). What a corrupted or missing `current/` would be
  restored from, and what "view my original files" (Settings) opens.
- `current/` - what every other consumer actually reads (`find_current()` for icons, `find_current_voice()` for a
  character's voice). Nothing today writes into it in place - the two copies are identical from the moment they're
  made - but keeping them separate is what makes a cheap, blind reset possible without asking the user to
  reconnect their dump.

`manifest.json` records what was found and copied (which icon archives, which locales, which character voice slots,
the source folder shown for reference only - it doesn't need to still exist afterward - and when). `status()` reads
it back for Settings and the Setup step; `done` requires both icon archives plus at least one locale (voice is
best-effort - a dump missing a few characters' files is a warning, not a failure). Each copied file's magic bytes
(`SARC` / `BARS`) are checked before it's trusted; anything that doesn't look right is skipped and reported rather
than copied.

**What this replaced:** an optional per-feature "Your game's files" folder setting (`game_files_dir`) that `ui_setup.py`
read live and `voice_api.py` read live for voice - meaning UI icons/text needed a mod to ship them or that folder to
still be connected, and *muting or replacing a character's default voice needed a ticked voice mod first* if that
optional folder was never set (true of most installs). Requiring the copy up front removes both: `_game_files()` and
`_voice_game_file()` now always resolve to the app's own copy, so every roster character
(all 50 have a `DRIVER_SLOTS` code, plus Gold Mario's own separate voice archive - 51 in total, verified byte-for-byte
against a real dump; see the comment above `DRIVER_SLOTS`) has a base voice to start from with no voice mod
ticked at all, and UI icons/text work with nothing ticked either. (The card's Voice row still shows only "Comes after you pick a mod" until the
character has a ticked mod - see "Voice editing" below - but that is a UI choice, not a missing base file.) `get_flow_status()`'s `setup.done` requires the copy
to exist (`game_files.status(mod_root).done`), so an install that's missing it is sent back to Setup rather than
silently degrading somewhere else in the app.

## Reference data: course internal names and music ids

Each MK8DX course has a real, fixed internal folder name inside `romfs/Course/`
(e.g. Water Park is `Gu_WaterPark`) and a real, fixed race-music id embedded
in its BGM filenames (e.g. Water Park's music is `pBGM_WU_WATER_PARK_F/N.bfstm`)
that the game actually uses - neither has anything to do with what a
GameBanana mod happens to be titled. A mod can be correctly *about* one
course while its files (or its music) are wired to replace a *different*
course's slot, which otherwise only shows up as a confusing conflict against
whichever mod really owns that slot, if it shows up at all.

`roster.json` records both, per course, for all 96 courses:
`"internal"` (the `Course/<id>/` folder name) and `"music"` (the BGM id -
for a Booster Course Pass course this is just its own `Cnsw_NN` internal id
reused verbatim; every base-game/Wii-U-DLC course has its own, otherwise
unrelated-looking id instead, e.g. Twisted Mansion's romfs id is
`Gu_HorrorHouse` but its music id is `WU_HAUNTED`). `mod_manager.py`
cross-checks every course download against both independently, flagging a
mismatch right on the file row instead of leaving it to be discovered later
(or never). A mod that bundles no music at all - most don't - isn't treated
as suspicious; only bundled music confirmed to belong to a specific *other*
course is.

Source: the [Mario Kart 8 Deluxe Information Dump](https://docs.google.com/spreadsheets/d/1B0XM1LqJxmp5L5pD3xgSSc3nBNcBAgVHL6q9RcIO_8E)
spreadsheet (a community datamine, linked from
[this GameBanana tutorial](https://gamebanana.com/tuts/16319)), cross-checked
against [GameBanana's Wave 1](https://gamebanana.com/tuts/14836) and
[Wave 2](https://gamebanana.com/tuts/15196) course-name tutorials and against
real downloaded mod content - all three agreed everywhere they overlapped.

The same spreadsheet has two other tabs not used by this app: `Objects` and
`Collisions`/`Coordinates` (MapObj AI behavior, KCL collision-flag, and BYAML
coordinate-system references - all track-*building*-level detail, no use for
a mod *merging* app like this one).

## Merge behavior: `Audio/Static/BGM.bars` is never merged in

`romfs/Audio/Static/BGM.bars` is a single, game-wide table of short music
"prefetch" clips - one per track - that plays for the first second or so of
a course while the real, full-length music streams in separately from its
own `.bfstm` file in `Audio/Resource/Stream/`. It isn't a per-course file,
even though plenty of course mods bundle a full rebuilt copy of it just to
patch their own track's prefetch entry.

That makes it the single biggest source of merge conflicts between mods for
*different* courses in the same cup: two course mods that have nothing else
to do with each other can still collide the moment both happen to include
their own copy of this shared table. Before excluding it, every currently
downloaded course mod that bundles it was checked, and all of them also ship
their actual music as their own uniquely-named `.bfstm` stream file - so none
of them actually depend on `BGM.bars` to play their music; it only buys back
that ~1 second of prefetch polish (several, including the mod behind N64
Bowser's Castle, turned out to just be redistributing
[ThatOneMartini's "Tiny BGM.bars"](https://gamebanana.com/mods/456533)
verbatim, byte-for-byte, which does the same thing on purpose game-wide).

Given that, `mod_manager.py` (`_MERGE_SKIP_RELPATHS`) never copies this path
in from *any* mod, in either Merge & Stage or the live conflict checker - the
base game's own vanilla `BGM.bars` is always left in place. This is a
heuristic based on everything downloaded so far, not a guarantee: a course
mod that delivered its music *only* through a `BGM.bars` prefetch entry, with
no separate stream file, would have its music silently dropped rather than
flagged as a conflict. None of the mods checked so far do this - the "tiny
bars + stream files" approach is clearly the community-standard convention -
but it's worth knowing the failure mode exists if a future download behaves
differently.

## Merge behavior: packed `UI/*.sarc` archives are never merged in, loose UI textures are

Course and character mods commonly bundle their own copy of `romfs/UI/...`
content alongside their real mod files. Two very different things hide under
that same folder, and `mod_manager.py` (`_compute_claims()`) treats them
differently on purpose:

- **Packed archives** (`common.sarc`/`menu.sarc` for character-select icons,
  `message.sarc` for a locale's entire text table - including every course's
  display name) bundle *every* character's icon, or *every* string, in one
  file - never just the one entry a mod actually changed. Merging a mod's own
  copy in directly would silently wipe out every other character/course's
  icon, or every other piece of text, not also present in that mod's own
  rebuild. These are always skipped, exactly like `BGM.bars` - the base
  game's own copy is left in place. The safe way to update them is to build
  **one** combined file from all ticked mods - "Menu icons & text" below does
  that automatically, as part of every commit (hand-injecting with Switch
  Toolbox still works but is only the fallback; see the in-app Help page and
  "UI Icon Worklist" in Settings).
- **Loose, individually-named UI textures** - most commonly a course's own
  `UI/cmn/menu/ym_CoursePict_<internal id>.bntx` select-screen thumbnail and
  `UI/cmn/ending/ym_AwardBG_<internal id>.bntx` results-screen background,
  or a character mod's own kart-select portrait textures - are a completely
  different, safe case: the internal id baked into the filename means nothing
  else can plausibly claim that exact path, so they're merged in normally
  like any other romfs file.

This used to be a single blanket rule (skip *everything* under `UI/`,
regardless of file type), inherited from the character-icon case without
being re-checked for courses - which meant every course mod's own select-
screen icon and results background was being silently dropped on every
merge, even though it was perfectly safe to include. Confirmed by scanning
every currently downloaded course mod's own `UI/` folder: the packed-archive
convention (`.sarc`) and the loose-per-course-texture convention (`.bntx`)
never overlap, so the fix is a plain file-extension check, not a per-category
guess.

Nothing skipped this way is silent any more: the merge log lists every skipped
`.sarc` by mod, warns when a mod contained *only* packed archives (so ticking
it did nothing), and such mods carry a "packed archive only" badge in the
"Mods to merge" list (`Api.get_packed_only_units()`). In the **UI** category,
downloads with no romfs that are UI art (PNG/texture icon sets, a bare
`.sarc` - `looks_like_ui_art()`) are classed `ui_assets` and listed in
Settings' UI Icon Worklist under "UI mods", same as character icon dumps.

## Menu icons & text: combined character icons and course/character names

Not a step of its own (it used to be - see "Phase 3" in the note at the end of "The guided flow"
below) - `_build_ui_archives()` (`mod_manager.py`, on top of `ui_setup.py` + `ui_archives.py`) runs
automatically inside `merge()`, right before its own file-copy pass, whenever anything needs
combining (`_ui_build_needed()`: a ticked mod's own `common.sarc`/`menu.sarc`/`message.sarc` for the
current language, or the user's own icon/name overrides). No outside tools, and nothing to run
first - committing is enough.

The Commit page itself only shows a lightweight, informational warning when there's something to
combine (`"ui-archives"` in `_commit_summary()`) - no card, no controls. Language is a set-once,
rarely-touched preference (already asked once during the Setup wizard), not something worth a
dedicated section competing for space on Commit every single time; the warning's **Open Settings**
button (`"action": "settings"`) is there for the rare time someone does want to change it.

Everything about menu icons & text that isn't "just commit" lives in Settings' **"UI icons & text"**
card (`renderUiSetupSettingsCard()` in `src/ui/js/settings-panels.js`) instead:
- **Language** (`ui_setup_locale`; `message.sarc` is per language, icons are not) and an optional
  "also build the other English" box (`ui_setup_extra_english`) - both persisted settings, read by
  `merge()` at commit time.
- **The rare pick-which-mod-wins conflict** (`renderUiArchiveConflicts()`) - only when two different
  ticked mods change the exact same icon or text entry to different values (`_conflicts()` in
  `ui_setup.py`); `_winners()` already has a sane default (the first mod, alphabetically) so this is
  an optional override, never something that blocks a commit, and it's the only piece of the old
  per-mod diff view that survived - everything else it used to also show (a preview of every mod's
  icon/text changes, one archive at a time) was dropped: it's redundant with what the character/
  course card's own Menu look already shows, in the context of that one character, which is a
  better place to review it than a second, decontextualized copy here.
- A status line per archive, **Open the folder**, **Undo** (removes the built files; the game falls
  back to its own), a manual **Rebuild now** (`build_ui_setup()` - `_build_ui_archives()` plus
  staging the result immediately, since there's no commit right after to do that for it), and
  "Advanced: do this by hand" for anyone who'd rather use an external tool.

**Guessed names** (`_guessed_names()`, `"guessed-names"` Commit-page warning) still opens its own
small modal to confirm or edit each one (`openGuessedNamesModal()`) - that one stayed a Commit-page
warning rather than moving to Settings, since it's tied to the mods currently ticked, not a
standing preference. An **icon pick needed** (`_auto_icons()`, `"icon-choice"` warning) still links
straight to the character's own card, same as before.

The actual build - writing the files into `ui-icons/`, backing up anything it replaces to
`ui-icons-backups/`, then re-reading each built file to check every change is really in it (a green
tick per file) - happens inside `merge()`, so its result is just part of the normal commit log. A
commit calls `_build_ui_archives()` directly (no separate staging step - the copy pass right after
already picks up `ui-icons/romfs`), which is what removes the old "build, then also stage it"
duplication; Settings' manual Rebuild now calls the public `build_ui_setup()` wrapper instead, which
adds that staging back since there's no commit right after to do it.

`_ui_signature()` is what "has anything changed since the last build" means: every checked mod's
packed UI archive (path/size/mtime), the language + "also build the other English" choice, the
conflict picks, the user's overrides, and the base game files' own mtimes. A commit's own
staleness (`commit.stale` in `get_flow_status()`) folds this in too - so changing only the
language, with no mods re-ticked, still makes a re-commit necessary, exactly as if a mod had
changed. (This used to be tracked as a separate "ui" step's own done/stale, with its own gate on
`recommended` - folding it into `commit.stale` was the real fix here, not just a rename, since the
old `_ui_signature()` never actually included the language choice despite its docstring claiming it
did.)

**Your game's own files (required).** The finished `common.sarc` / `menu.sarc` /
`message.sarc` are the game's own file with the changes swapped in, so the app
needs a complete copy of them to start from - and it can't ship one (they are
Nintendo's files, and a copy built from mods wouldn't be the game's own anyway).
A required Setup step copies them once from a folder extracted from the user's
own game into the app's own local copy - see "Base game files" above
(`game_files.py`, `find_current()`). Those files join the analysis as a source
flagged `vanilla`: they are the truth for "what the game has", so a mod's
change is simply what differs from them, the base of every build is the user's
own game version, and icons/names work even when no mod ships these files. The
older "borrow a mod's copy, or do nothing at all when none ships one" analysis
still exists in `collect_sources()` for the case `_game_files()` comes back
empty, but that should now only happen before Setup finishes. An archive
nothing changes is not built (a stale built file is removed), so the game's
own file is used as it is.

How it works, since there's no per-mod "diff" to read (the comparison below is
what is used when no game files are given): every mod ships a full
copy of the same game file, so each copy = the game's file + that mod's
changes. The analysis compares all copies; the value most copies agree on is
"vanilla", a value unique to one copy is that mod's deliberate change. Two
noise rules keep it honest: strings whose visible text matches vanilla (only
hidden control codes differ - a different game region/version) are ignored,
and a copy with lots of unrelated differences (built from another game
version) only contributes changes related to what the mod is filed under. The
base file is the copy with the most entries / newest game version. Anything
that can't be inserted safely (a screen the base copy doesn't have, a picture of another
shape or format) is reported and left vanilla. A plain RGBA picture that is only a different
size (same proportions, within 5%) is scaled to the game's size (`ui_setup.rescale_texture`).

Format notes (measured, `ui_archives.py`): `common.sarc`/`menu.sarc` are SARCs
of Yaz0 `.szs` entries; the character-icon entries (`cm_L_CharaIcon_00.szs`,
`mn_L_CharaIcon_00.szs`) are nameless SARCs holding a small layout blob and one
BNTX with every icon as uncompressed RGBA8, so an icon change is an in-place
same-length pixel swap. `message.sarc` is a plain SARC of MSBT files; names
are labelled strings. Writers reproduce the original bytes exactly when
nothing changes (tested on the real files). Caveats: the rebuilt entries are
Yaz0 "stored" (valid, but ~12% larger, no compressor), and none of this has
been run on Switch hardware.

## Look and feel

- **Tooltips** are one custom element instead of the browser's own. Every `title="..."` in the app (in the markup or set from
  code, on anything that appears later too) shows it, so nothing had to be rewritten: while the mouse is over an element its
  title is taken off (that is what stops the browser's own tooltip) and put back when the mouse leaves. It is a dark card with
  an arrow, appears after a short pause over each element (moving on to the next one starts the wait again), goes under the element (above it when
  there is no room), stays inside the window, and disappears on click, scroll, key press or window resize. Lines of a title
  become lines of the tooltip and a "Label: text" line gets its label picked out. Tab to an element and it shows too.
- **Scrollbars** are slim and use the app's colours (light and dark). The window's content is capped at 1800px wide
  (`--app-max` in the stylesheet): on a wider window the extra room goes to the sides, and the header, tabs, pages and
  footer stay lined up.
- **Waiting is shown, not hidden.** A character tile with ticked mods pulses until the app has read what those mods change
  (the icon and name) - on opening the app, and again after a tick. In a character's card, ticking or unticking a mod turns
  the Name and Icons sections into a loading state at once (the status line says "reading the appearance...", the chip says
  "Reading...") until the new answer is drawn; a course's Menu look card does the same ("Reading the mod's menu files...").

## The guided flow: step bar, Next button, Commit page

The app walks you through four steps, shown in the header itself - one row holding the title, the four steps and
two icon buttons (Refresh, the circular arrow, which turns while it reloads; Settings, the gear) - and a
**Next** button in the bottom-right corner - flush with the window's right edge, a rectangle with barely rounded corners
and a slanted left side (bottom-left sticks out further than top-left), like the game's own (`get_flow_status()` in
`mod_manager.py` is the single source of truth; the frontend just renders it):

1. **Setup** - first run: master folder (existing flow), then a required wizard: game version
   (`set_game_version()`; a known version also sets `game_build_id`, which the code-patch "wrong
   version" checks use), **your game's files** (required, no skip - see "Base game files" above),
   options (NSFW, Advanced mode), and Switch language (`ui_setup_locale`). `setup.done`
   (`get_flow_status()`) is true only once both the `setup_done` flag is set AND the base-files
   copy exists (`game_files.status().done`) - a base-files copy that goes missing sends the step
   bar back to "Setup" even if the wizard was completed before. Reopen from the step bar. The
   `pywebviewready` startup handler checks this too, not just whether a master folder is configured -
   a folder being picked (which happens immediately, before the wizard even opens) isn't the same as
   setup being finished, so closing/reloading the app mid-wizard used to silently drop straight into
   the main app on the next launch instead of resuming it; it now reopens the wizard (with no Close
   button, same as a genuine first run) whenever `setup.done` is false.
2. **Choose mods** - the Character / Course / Vehicles / More / Full List tabs,
   with per-tab tick counts.
3. **Commit** (was "Merge & Stage"). The page asks `preview_commit()` (a dry
   run: claims, clashes, warnings) as soon as it opens, shows every clash as a
   settle-it-here card, and blocks the Commit button until none are left. When
   there's menu icons/text to combine, that's just a lightweight warning here
   (linking to Settings) - the actual `merge()` call itself builds it
   automatically, right before its own file-copy pass. The result comes
   back structured (`counts`, `warnings`) with the old text log (now including
   what got built) kept under "Details (full log)". The sidebar Output log was
   removed.
4. **Copy to Switch** - checklist + "It works!" (`mark_switch_done()`).

**Phase 3** (2026-09-22) removed what used to be its own fifth step, "UI icons & text" - a whole
page just for picking a language and pressing Build, when the analysis and the build were already
fast and automatic underneath it. Checking guessed names and picking between conflicting icon
versions moved onto the Commit page itself as warning cards; language, the (rare) pick-which-mod-
wins conflict, and Open the folder/Undo/manual rebuild/"do this by hand" all moved to Settings
instead - deliberately not a Commit-page card of its own, since language is a set-once preference,
not something to review at every commit. See "Menu icons & text" above for the full picture.

"Done"/"stale": a commit records `last_commit` (a signature of the ticked
mods + every left-out file) and, when anything needed combining, `last_ui_build`
(see "Menu icons & text" above for what's in that signature) - `commit.stale`
is true if *either* no longer matches, so a language change alone (no mods
re-ticked) still calls for a re-commit. The Switch confirmation is tied to
both signatures together. Change any input and the step turns amber again.
`flowNextTarget()` in the frontend decides what Next says from the page you're on.

## Conflicts: leaving files out

Two mods writing different bytes to the same romfs path clash. A clash is
settled by leaving the file **out of the loser** - stored in
`excluded-files.json` as `{mod key: {normalised path: {path, reason, kept_from,
added}}}`, applied in `_compute_claims()` before any claim is recorded. So the
same mechanism covers "keep Steve's emblem", "use the game's own file" and a
plain "don't copy this file from this mod" (a mod popup's **Files** button lists
everything a mod ships with a checkbox each).

* `_conflict_groups()` groups clashes per *set of mods* (one decision for 40
  files), classifies the files (`path_kind()`), reports how much of each mod is
  affected (`4 of 37 files`) and suggests keeping the mod that belongs in that
  slot (a mod filed under Funky Kong that really replaces Donkey Kong's model loses
  to the actual Donkey Kong mod - `_slot_mismatch()`), then the one that relies on
  the files most, then the name that sorts first.
* `resolve_conflict_group(mods, paths, keep)` excludes the paths from every
  mod but `keep` (skipping byte-identical copies); `keep=None` = the game's own
  file. Code patches (`exefs/...` pseudo-paths) can't be split - only "untick".
* Cards are `buildConflictCard()` in the frontend and appear in the mod popup
  (clashes with *any* ticked mod, not just the same item's), the Commit page and
  Settings > "Conflicts & left-out files" (always visible; Advanced mode no
  longer gates it). The older `conflict-resolutions.json` priority list is
  still honoured when present but nothing writes to it any more.
* Exclusions of a mod that is no longer downloaded are dropped lazily.

## Menu look: your own icons and names

For a mod that ships no menu icon or new name, a character/course popup's
**Menu look** card (`get_menu_look()`) shows what the select, map and results
icons and the name will be - and whether each is the game's own, a mod's, or
yours. You can pick a picture (one of the mod's GameBanana screenshots or a file
from your computer; the existing crop dialog, square) or type a name.

**The card is never stale.** It has no cache: it is re-read every time the popup opens, a
mod is ticked/unticked, or a download finishes (`refreshBehindModal()` -> debounced
reload of the open card). When exactly one ticked mod ships the packed menu files and
there are no game files to compare with, nothing can be diffed - so if that mod is filed
under this character its icons are labelled "In a mod's files" (not "Normal"), and its
name is recognised by comparing its text at the character's entry with the game's name.

**Choices are intent, saved without any game data.** Menu look works the moment a
mod is added, with no game files and no mod shipping the shared menu files:
`get_menu_look()` reads only `ui-overrides.json` (pictures by slot; names by
`"<kind>|<item>"` -> text, in `names`), the automatic loose-picture picks, and - only
when some ticked mod ships packed menu files, or game files are chosen - the analysis
of those (to say what a packed mod changes and show the game's own thumbnails).
Nothing is resolved against a base until the next commit builds it: that is when a
picture is resized to the target texture and a name is matched to its text entry
(`apply_overrides()`), and when anything that doesn't fit is reported ("couldn't find
'X' in the game's text"). Base game files are required at Setup, so there's always
something to build against by the time this runs; the only real risk left is a dump
that's missing a specific locale, which `game_files.status()`'s `problems` list
already surfaces in Settings. Name overrides saved by label in older versions
(`strings`) still apply.

They're stored in `ui-overrides.json` and enter the UI plan as one more "mod"
called *Your changes* (`ui_setup.apply_overrides()`); its picks always win, so
building, verifying and the review screen treat them like any mod's change. An
icon is resized to the target texture's exact size, converted to RGBA8 and
swizzled with `bntx_encode._swizzle` (checked to be the exact inverse of the
previews' decode) so it's the same same-length byte swap as any other icon. A
name is matched to its numeric label in `Common.msbt` (characters 1000-1099,
courses 1400-1599 - the short and cup-line variants), from an English message
archive of the plan. Building needs the game's own menu files (see above) or, failing that, a ticked
mod that ships them to use as the base copy - but choosing does not.

**Character Select layout.** On a window at least 1100 px wide (`DOCK_MIN_WIDTH` in `src/ui/js/character-select-layout.js`) the
screen is: the character grid on the left (55% of the width) and the card of the selected character - mods
to merge, menu look, GameBanana mods - on the right (45%), two equal-height columns, and under them a
bottom row with the character's **name plate** in the middle and the Next button at the right end. The
proportions are fixed, so the screen looks the same at every window size. The grid always shows every
character with no scrolling: `fitCharacterGrid()` picks the biggest square tile that fits the column by
width AND height (a wide-but-short window gets smaller tiles, not a taller grid), the gaps and type scale
with the tile, and the grid is centred in its column. The board behind the grid is only as tall as the grid (it
is not stretched to fill the column) and is centred vertically in the space, so the room the grid has is
measured from the layout, not from the board. The 8 columns (the in-game arrangement) never change. (The
tabs are called **Characters** and **Courses**.) A character tile with an icon is just its icon - no fill, no
shadow and no coloured ring - while a tile without one keeps a grey border (2 px) (a conflict still shows a red one, on either) - and the icon fills nearly the whole tile in
the wide layout.
There is always a character selected - Mario when the app opens, afterwards the one you last viewed - so
there is no empty state and no Close button. The selected tile gets the same pulsing yellow corner brackets
as the selected cup on Course Select, and a group tile (Inkling, Villager) stays marked while you choose
between its two characters in the card. The name plate shows the name as the menus will show it (the mod's or
your name from the Menu look, else the game's own; for a group tile under the mouse, each variant's: "Boy: Yoda · Girl: Pinkie
Pie") in white on a
black plate that fades to transparent at both ends. Below 1100 px there is no card and no plate: clicking
a character opens the pop-up as before (nothing pops up by itself when the window shrinks), and growing
the window past the threshold moves an open pop-up into the card. It is the same card-building code
(`openCharacterModal()` builds into whichever container `beginDetail()` picks); the
other tabs and the Settings pop-ups are unchanged.

The grid sits on a board (a light translucent panel, `rgba(219,219,219,.25)`, slightly rounded, with a ridge border of the same colour and opacity)
and is centred in it both ways. Hovering a tile doesn't move it; instead one white corner-bracket frame
(`makeHoverFrame()`) slides smoothly to whichever tile the mouse is over and fades out when it leaves the
grid (the yellow brackets of the selected tile stay on top). Course Select uses the same helper for its cup
tiles and course tiles, replacing their old lift-on-hover.
The four course tiles are rectangles with angled (chamfered) corners, not circles, drawn in two layers
because a clip-path can't carry a border, and all four sit in one large container with a white-to-grey
gradient (`#course-strip`). In the wide layout the card has no title of its
own: the game's character name is on the name plate, after the modded name, smaller and dimmer -
"Pizza (Kamek)" (nothing extra for an unmodded character); the pop-up on small windows keeps its title.

**Names we guessed.** The Commit page shows a "names were guessed" warning card whenever a guessed
name (see "Ticking a character mod tries to name the character") hasn't been confirmed yet; its
**Review names** button opens a small dedicated modal (`openGuessedNamesModal()` /
`drawGuessedNamesModal()` in `src/ui/js/menu-icons-text.js` - reusing the same row-building logic the old standalone
page used) - one row per character: the name in an editable box, **Confirm** (which becomes **Save
name** once the box is edited) and **Use the game's name**, plus **Confirm all as shown**. A wrong
guess would otherwise be built into the game's menus. A guess counts as confirmed once the Name task
itself is confirmed for that character's current set of ticked mods - either here, or with the
card's own **Use this name** - since Name and Icons are independent tasks (see "Name and Icons"
above): Icons' "Looks right" no longer settles it. Confirming here (or on the card) settles only
Name, so the tile's check mark (which needs both Name and Icons) is unchanged if Icons is still
open. Saving an edited name makes it the user's own (it leaves the list),
"Use the game's name" drops the guess for good (`declined_names`), and ticking a different set of
mods brings a changed guess back for another look. The record is the `names` part of
`look-reviews.json` (`get_guessed_names()`, `confirm_guessed_name()`; `set_item_name()` /
`clear_item_name()` take `mark_reviewed=False` for this list).

**The character card.** A character's card (docked beside the grid, or the pop-up on a small window) keeps
everything about that character in view at once. At the top: the name it will have in the game (when a mod
changed it), a sentence saying where things stand ("2 mods in use - appearance needs a look") and a status chip
(*No mod yet*, *Choose a mod*, *Needs a look*, *Done*).

* **Mods** - the mods in use are always shown as rows, never folded into a sentence: the mod's whole name
  (long ones wrap), what it replaces (*Character*, *Kart*, *Wheels*, *Glider* - `unit_parts()`) and, with a speaker icon,
  *Voice* when it ships voice files (see below), the character's
  own mod first. The chips beside a name never share the row's fill (a checked or hovered row is tinted): what a mod replaces is an
  outline, and the chips that do something (pictures, voice) are filled with the card's colour, outlined in the accent, and fill in on
  hover. Open folder, Files and Remove are behind the **...** button on each row, which opens a small popup menu (the same kind as in the Icons table; Remove, in red, still asks first). The mods that aren't
  in use, and the tick boxes, are behind **Manage** (it becomes **Done**); with nothing ticked yet the whole list
  is open. Variants of the same files (colours, menu-sound options) are pick-one, and so are mods that each
  replace the same character's model: ticking one unticks the other, and "Select All" ticks only one of them
  (`modelGroup()` - the mod's *Character* tag plus the slot it writes to). Companions (kart, glider, voices)
  are never affected. Underneath sits a quiet
  "+ Add another mod" row that opens the GameBanana section (paste a link or browse) in place; with nothing
  downloaded the card is just that section, open, as "Find a mod". Clash cards are always visible, above.
  A UI-icons-only companion download filed under this character (no romfs, so it can't be ticked - see
  "Which texture a loose picture goes to" above) still gets its own row here rather than being invisible just
  because there's no checkbox for it: `Api.get_icon_only_mods()` lists it with which of the three icons it's
  currently supplying, if any, and a **Use game default** button when it is. Such a download that would
  otherwise land on a bare numbered `(2)` name because it collided with a sibling mod's folder is instead
  named `<mod> (icon pictures)` at download time (`_download_and_extract_one`), so this row - and the tile's
  own hover tooltip - reads as what it is rather than looking like an accidental duplicate.
* **Name** and **Icons** - two independent tasks, each its own row (like **Voice** below them), greyed out
  until a mod is ticked. Confirming one never marks the other: a mod that only changes the name (or only
  changes the icons, or only swaps the 3D model with neither) leaves the *other* row reading "Nothing to
  check", and a character only counts as finished once *every task that applies to it* is confirmed -
  `mod_manager.py`'s `_review_state()` returns `name_applicable`/`name_done` and `icons_applicable`/`icons_done`
  as two separate pairs; `reviewFinished()` in `src/ui/js/tiles-and-review.js` is the one place that combines them (both true,
  or not applicable, for each). Each row is a short walkthrough the first time, and a **read-only summary**
  (status "Completed", with **Edit** right beside the title) afterwards:
  - **Name** - "What should Birdo be called in the game?": the preview (the icon and the name plate as the
    game's select screen shows them) where the plate is the name box, already filled in with the guess (or the
    mod's own name; empty means the game's own). **Use this name** (or Enter) confirms it - `confirm_guessed_name()`,
    so a guess confirmed here no longer appears in the Commit page's guessed-names review. It reads "Keep the
    game's name" when the box is empty. A name typed but not confirmed is kept as a draft (`nameDrafts`, per
    character and tied to the saved name it was typed over), so leaving the card never throws it away - the
    row shows it again with "You had started typing this name - it wasn't saved yet.". Afterwards, the summary
    is just the name plate and where it came from.
  - **Icons** - "Do these icons look right?", one plain line for where they come from, and the three icons as a
    small table (icon | name | description) - **Select screen** (shown when you pick your character), **Mini
    map** (the marker on the course map during a race) and **Results screen** (next to your name in the race
    results). The picture is the button: hovering (or tabbing to) an icon puts a pencil over it, and clicking it
    opens the picture window for that icon alone (for a character with colours, the colour shown). A small tag
    by the name says where the picture is from - *Mod*, *Yours* or *Made from Select*. A picture the mod
    doesn't have shows a dashed "+" and a line "Not in the mod. Use the Select screen one" (see below). A row
    gets a **...** menu only when there is something more to do to it - *Undo my picture* (back to the mod's
    picture, or the game default if it has none), *Use game default* (turns the mod's picture down) or *Undo*
    for a made picture - and the **...** in the table's header holds what applies to all three ("Use one
    picture for all three...", "Use game defaults"). **Looks right** confirms it. When a mod ships several sets
    of icon pictures, picking one comes first; when no mod supplies an icon, a nudge offers "Add a picture"; a
    character with no icons at all but a model-swap mod (nothing to preview) just gets a plain confirm button -
    "give it a glance in-game". Afterwards, the summary is the colour strip if there is one, and the same table
    with a **Source** column ("King Dedede UI", "Made from the Select screen", "Your picture", "Game default")
    and no pencils or menus.
  The picture window lists **Icons from the mod** first - the pictures the mods provide for the character (what
  they already bring into its menu icons, plus other loose pictures in mods filed under it or named for it;
  `get_mod_icon_pictures()`), then any a mod filed under this character has for **another character**
  (named for someone else; a deliberate choice to use one) - used as they are when clicked
  (`use_mod_icon_picture()`, no cropping); then the screenshots and "Choose a picture from your computer..." (a
  tile the size of a screenshot), which go through the crop step. Changing, picking or resetting an icon never
  counts as confirming Icons: the walkthrough stays open so you see the result - and setting or clearing a name
  from outside the Name row's own buttons (the Commit page's guessed-names review, "back to normal name") only
  ever confirms Name, never Icons.
  A character can be left half-way on either task independently; its tile keeps the amber dot until both are
  confirmed (or not applicable). Leaving is never blocked - clicking another tile or tab is fine - but
  unfinished work stays visible and is asked about once: the tile keeps its amber dot, the Choose mods stage
  reads "6 mods ticked - 2 to finish" (amber) and the Next button's tooltip says how many, and pressing **Next** (or
  the Commit / UI / Switch stage buttons) while any character is unfinished opens a gate - "2 characters aren't
  finished", the names, and "If you continue, they're used as they are now - and a name that was only a guess is built
  into the game's menus without being confirmed" - with **Review them** (a guided pass, below) and
  **Continue anyway**; Escape or a click outside stays put (`passUnfinishedGate()`, which asks the backend afresh via
  `get_character_tile_view()`). **Review them** walks through the unfinished characters one after another
  (`startReviewQueue()`): a bar on top of each card says "Reviewing unfinished characters - 2 of 3" with **Skip** and **Stop**;
  finishing the last thing it needed shows the completed summary for a moment and then opens the next one; at the end the bar reads
  "All done - every character is finished." with the next stage's button (or "Done - 2 skipped, still unfinished."; the
  button then goes on without asking again) and **Close**. A character whose mods change nothing visible has neither row's
  walkthrough ("Nothing to check" on both; Edit is still there, though it does nothing since there's nothing to walk
  through). On a narrow card the Icons table's rows stack (picture left; name and description right, the menu at
  the corner). (`clKebab()` is the small popup menu: it closes on any click elsewhere and on Escape.)

**Characters with colours (Birdo, Yoshi, Shy Guy...).** The game keeps one set of pictures per colour, so the
Icons row shows a strip of colour dots (each one that has a picture from a mod shows it; a "!" marks a
colour with a missing picture) and the three icons of the colour picked. The count of pictures a mod ships is
given as colours ("9 colours (26 of 27 pictures)") rather than a bare number. `get_menu_look()` carries a `per`
list (one entry per colour) on each icon slot for such characters.

**Filling in a missing Mini map or Results picture.** Mods often ship a Select screen picture but not the other
two, which would leave the game's own Mini map / Results picture next to a modded Select screen. All three
icons are square (128, 64 and 52 px), so the Select screen picture can stand in for the others - it is scaled
down when the menus are built, the same way the user's own pictures are. A missing icon's row says "Not in the mod" and
offers **Use Select screen picture**; when several are missing (in any colour) a line above **Looks right** offers
to fill them all. It is an offer, never automatic, and nothing is "checked" by it - the row then says "Made from
the Select screen" with an **Undo**. `fill_missing_icons(name, colour, kinds)` / `unfill_icons()`. A made
picture is stored with a fingerprint of the picture it was made from (`fill_sig` in `ui-overrides.json`) and goes
away by itself when that Select screen picture changes or its mod is unticked; a picture a mod really ships
always wins over a made one. Colour-variant `per` data carries the private `src` only inside the backend.

**After "Use this mod" (GameBanana).** Choosing a mod in the browse window (or pasting a link and pressing Fetch)
closes the browse and detail windows and lands on the character's card, scrolled to the mod. A mod with a single
file is downloaded straight away (with a progress bar); a mod with several says "Choose which files to download"
with the newest / fullest ticked; a single file that mentions another character in its name isn't downloaded
without a look. Once a download is finished and nothing else waits, the "Add another mod" row folds shut, and a
lone mergeable mod is ticked as before.

**Waiting.** Where content is coming (the appearance step, GameBanana results and details, the UI files being
read) grey placeholder shapes sit where it will appear, next to a spinner and a plain sentence; downloads and
builds show an indeterminate bar. (`loadingNote()`, `skeleton()`, `skeletonGrid()`; they stand still when the
system asks for reduced motion.)

**Menu pictures.** A character mod row that brings pictures for the menus gets a picture tag (a small picture icon, before the
speaker): the tooltip says which of *Select screen*, *Mini map* and *Results* it has ("... (no Results)"), how many versions
and colours, and - when its pictures are named for a different game character - which one. Clicking it opens a window showing them at their real sizes, one block per source: the mod's loose picture
files (one per version) and the pictures in its packed menu files, with a dashed "Not included" where one is missing (a
missing Mini map or Results can be made from the Select screen in the Icons row). The window only shows; you choose which to use in
the Icons row. It replaces the old *icon* tag on character rows (which meant "any .png/.jpg anywhere in the mod folder" -
screenshots counted, packed pictures didn't, and it opened Explorer); courses, vehicles and the other cards keep that tag. The
tag follows what the Icons row itself would find: `Api.get_unit_pictures(unit_keys)` (per unit: `kinds`, `versions`, `loose`,
`packed`, `colours`, `for`) and `Api.get_unit_picture_sets(unit_key, siblings)` (the previews), both over `_unit_pictures()`.
Loose pictures count for the unit they sit in, or for every unit of the mod when they sit beside the units (`siblings` says
which units the card has); packed ones count when the unit's `common`/`menu` file holds this character's icon textures (the
same reading `get_menu_look()` gives a mod's own packed file - it can't say which of them the mod changed).

**Voice files.** A mod that ships character voices is tagged *Voice* (speaker icon) on its row - ticked or not, so it
helps you choose - and a character whose ticked mods ship voice files gets a small speaker badge in the top-left of
its tile (the review dot is top right); the tile's tooltip says which kind and from which mod. The files are the
in-race voice (`romfs/Audio/Driver/Driver_<name>.bars`) and the menu voice (`romfs/Audio/DriverMenu/MenuDriver_<name>.bars`),
found by `unit_voice()`; `get_unit_slots()` returns `voice: {race, menu}` per mod and `get_character_tile_view()` returns
`voice: {name: {race, menu, from}}`. A mod whose voice files are for somebody else's slot (the *Replaces ...* badge) gets
the row tag but not the tile badge. The tag means "voice files are there", not "the voice is different from the game's":
telling those apart would mean comparing against the game's own audio, which the app doesn't have.

**Playing the voice.** On a mod row the *Voice* tag is just a speaker icon (ticked or not - handy for choosing between
menu-sound options). Clicking it opens a window listing every sound in
the mod's voice files - character select, during the race, horn - each with its own round Play button and length;
pressing a button again stops it, and only one sound plays at a time (another line, closing the window or opening
another card stops it). The tooltip on a line is the game's own name for it (`pVO_CPC_OVTAK2`). The readable names are the
app's own guess at the game's abbreviations (`voice_audio.clip_label()`); the ones that aren't clear are left as spelled.
How: `voice_audio.py` reads the `.bars` archive (a table of sounds with their names), and decodes each sound - a
BFWAV, which for the game's voices is DSP-ADPCM in mono or stereo at any sample rate; 8/16-bit PCM also works - into a
16-bit `.wav` in plain Python, no audio libraries. `Api.get_voice_clips(unit_key)` lists a mod's sounds and
`Api.get_voice_clip(unit_key, clip_id)` returns one as base64 (`clip_id` is a place in the mod's voice files, never a
path); the page plays it with an `<audio>` element at 70% volume, because a
few mods' voices are mastered so loud they clip. A file the app can't read (cut short, another encoding) is said so in
words under the row. Nothing is written anywhere.

Only characters get this card; courses, vehicles and the More tab keep the old one. (`buildCharacterLook()`,
`assembleCharacterCard()`; the mod rows, Files panel, clash cards and GameBanana section are the existing
ones, recomposed.)

**Checking a character's look.** A character with ticked mods gets a marker on its tile until Name and Icons
are both confirmed (each only for the task that applies to it - see "Name and Icons" above): an amber dot =
"ticked, something not checked", a green tick = both checked or not applicable (no marker = no mods; the
hollow ring = mods downloaded, none ticked). Icons has its own **Looks right** button (with **Undo** once
checked) confirming the icons shown above it; Name has its own **Use this name**. The two never mark each
other - using your own picture, or choosing "back to normal" for icons, only ever confirms Icons; setting a
name, or choosing "back to normal" for the name, only ever confirms Name. Icons needs checking for a
character with a model mod of its own (not another character's slot) or any changed icon; Name needs
checking for one with an actual name change (typed, the mod's own, or a guess) - a mod with only voices or
kart parts leaves neither to look at. What was checked is stored in `look-reviews.json` (`characters` bucket
for Icons, `names` bucket for Name) as a signature of the character's ticked mods, and every signature ever
checked is kept: ticking a mod off and on again is still checked, while a different set of mods (a new one
ticked) needs looking at again, for both tasks. Everything starts unchecked (`get_character_tile_view()`,
`_review_state()`, `confirm_guessed_name()`, `mark_icons_reviewed()`, `unmark_icons_reviewed()`).

**Keeping the tiles quiet.** In the wide layout a tile that shows a picture has no name label - which is
most of them once base files are set up, not just modded ones: the name plate under the grid follows the
mouse (hover any tile and it shows that character's name, plus the game's name in brackets for a modded
one), and falls back to the selected character when the mouse is elsewhere. A tile with no picture at all
(no base files yet, or nothing to compute one from) keeps its name, and on a small window (no plate) every
tile keeps its name. The
"1/4" (ticked / downloaded) badge is off by default (`show_tile_counts`, Settings > Character Select): a tile
with mods downloaded but none ticked gets a small hollow ring instead, and the tile's tooltip still says
"3 of 14 mods ticked". The red "!" conflict badge and the attention dots are unchanged. Course and vehicle
tiles keep their badges.

**The character grid shows every tile's actual look, not just the modded ones.** Once base game
files are set up, an untouched character's tile shows the game's own select-screen icon - the same
picture `get_menu_look()` already draws on the Character screen, just reused rather than thrown
away (`get_character_tile_view()`/`get_character_looks()`, one pass over the plan for every tile).
A character a mod (or you) actually changes shows that icon instead - the first available of the
select-screen, results and map ones, preferring an actually-modded kind over a merely-vanilla one
so a mod that only touches, say, the map icon still wins the tile - with the modded name under it
instead of the game's. A tile with nothing ticked stays faded (`.no-mods`, unchanged) so it's still
obvious at a glance which characters you haven't touched; before base files are set up, or for a
character with nothing to compute a picture from at all, the tile falls back to its plain badge and
name as before. Hover a tile to see where the name came from (the tooltip no longer mentions the icon - the
tile's picture shows that, and clicking the tile shows the rest), and "No mods yet" for one with
nothing downloaded (no gray text on the tile itself for that anymore; it only lives in the tooltip).

**The character's select sound.** Clicking a character's tile plays the character-select voice its ticked mods bring (the
"Character select" sound in a `MenuDriver_*.bars`: `Api.get_select_voice()`) - whether or not its appearance is finished -
and so does the picture on the Villager / Inkling tile or that card's Boy | Girl switch, and the moment a character's
appearance becomes finished (its look checked, or a mod with nothing to check ticked). While it plays, the speaker on the tile
lights up and its two waves pulse. A tile that has such a sound says so in its tooltip ("Select sound: click to hear it";
`get_character_tile_view()` reports it as `voice[name].select`). The speaker itself is still about voice files in general:
a mod with only in-race voice gets it too, and clicking that tile plays nothing. Not a mod whose voice files are for another
character's slot, and not a voice file that was left out of the merge; with several mods that bring one, the first ticked one.
It uses the same one-at-a-time player as the Voice lines window (a new sound stops the last), at 70 % volume. Off with
Settings > Character Select > "Play a character's select sound".

**Villager and Inkling (one slot in-game, two characters).** Clicking their tile opens a card straight away - there is no
"which one?" step. At the top of the card a two-part switch moves between the two (Boy | Girl, Girl | Boy for Inkling): each side
shows its own picture, its mod's name (or "1/2 ticked", "no mods yet") and its review dot / tick, and it redraws as you tick
mods. The card opens on the one that still needs its appearance looked at, else the one with ticked mods, else the one you used
last (clicking the tile again while one is showing keeps it). On the grid the tile shows both: when either has a picture
(the game's own counts too, so this is now the common case once base files are set up), two smaller pictures sit on the
diagonal (first option top left, second bottom right), and a variant with nothing to show a picture from at all is a dashed
placeholder with its label; clicking a picture opens that variant. The tile does not cycle between them - half the information
would be missing at any moment, and motion means "loading" on the grid. With no picture on either, the tile is the normal
gradient one. Hovering the tile puts "Boy: Yoda · Girl: Pinkie Pie" on the name plate.

**Ticking a character mod tries to name the character** (`sync_auto_names()`, run by every
`save_checked()`, so every way of ticking is covered). Only mods that replace the character's
MODEL (`Driver/*.szs`) and belong in that character's slot count - voice-only, kart-only and
"replaces another character" mods don't. In order: (1) the mod's own text - a `message.sarc`
with a different name at the character's entry - in which case nothing is stored (the UI step
applies it); (2) the mod's name (GameBanana's, else its folder's), cleaned by
`suggest_name_from_mod()` ("Sandy Cheeks in Mario Kart 8 Deluxe" -> "Sandy Cheeks"; a name that is just
the character's own, too long for the menus (> 24 characters) or only noise words is dropped);
(3) the folder inside the mod. The guess is stored in `ui-overrides.json` flagged `"auto"`, so it
disappears when the mod is unticked, never replaces a name you typed, and once you use "Back to
normal name" on it, it is never guessed again (`declined_names`). The Menu look card says
"guessed from ...". Like any name it takes effect when the UI step is rebuilt.

**Packed menu files beside `romfs/`.** Some mods put `UI/cmn/common.sarc` etc. (or
`icons/common.sarc`, `Character name change files/message.sarc`) NEXT TO their `romfs/`
instead of inside it. `ui_setup.unit_extra_archives()` finds them by what they are, not by
folder name: `common.sarc`/`menu.sarc` files that really hold the character-icon entry; a
`message.sarc` in a language folder, or - with none - one whose text is English (it counts
for USen and EUen; a non-English one with no language folder is not guessed). The ones
inside `romfs/UI` win; the others only fill in what is missing. They are never staged
(a packed archive can't be copied straight in), but they count toward the Commit page's
"N mods change menu pictures or names" and are combined in the UI step like any other.

**Loose icon pictures.** Many mods don't ship the packed `common.sarc`/`menu.sarc`
at all but a folder of PNGs named `tc_Chara_<name>^l.png`, `tc_MapChara_...`,
`tc_edChara_...` (meant to be injected by hand with Switch Toolbox). The UI
analysis never read those, so such a mod looked "Unchanged". They now show up
under the Menu look card (`get_loose_icon_sets()`; a mod's own folder is
scanned, skipping `romfs/`) grouped into versions by the suffix Windows added to
duplicate names (`^l`, `^l1`, `^l2` - a mod often ships one per costume).

* **One version -> automatic.** For a character with exactly one ticked mod that
  ships pictures, and exactly one version of them, `gather_auto_icons()` uses
  them for that character (the pictures are named for the mod's own character,
  so the mod's *filed-under* character decides where they go). They enter the
  plan as their own variant, "<mod> (icon pictures)" (`is_auto`), shown in Menu
  look as "Automatic". Never applied where a packed archive already changes that
  icon, where the user chose icons, or where the user turned them down ("Back to
  normal" is remembered in `ui-overrides.json` > `declined`).
* **Several versions -> asked.** The character lands in `needs_choice`: its Menu
  look card shows the versions with thumbnails and a **Use for <character>**
  button (`use_loose_icon_set()`), the UI step and the Commit page list every
  character still waiting, and the step bar turns amber. Until picked, the
  game's normal icons are used.
* Pictures are recognised by name (`tc_..._<name>.png`, with or without the `^l`;
  "... Map.png"/"... Menu.png"/"... Common.png"), or - in a folder whose name says
  `UI` or `icon(s)` - by exact size when they have no telling name: 128x128 is the
  select icon, 64x64 the map icon, 52x52 the results icon (at least two of the
  three must be there). A single picture beside a `tc_` set fills the kind it lacks.
  Pictures told apart in *different* ways count together when they sit in the same folder: `UI images/Menu.png`
  (by its name), `Race Mini Map.png` (by its name) and `Race end.png` (only by its size) are one set - two or more
  different icons in a folder called `UI`/`icons`, or every one exactly the game's size for what it is (Pikachu in
  MK8D). One picture per icon (the first by name). As a last resort - only when the mod has no set at all - a folder
  holding all three exact icon sizes is icons whatever it is called (`Image Files Used/128.png, Race.png, 52.png`);
  next to a real set those are copies and are ignored, so they aren't a second version.
  Pictures inside a mod's `romfs/UI` count too (some authors leave the pictures they made there - Iggy's
  `romfs/UI/Common/tc_MapChara_Iggy^l.png`, Toad's `romfs/UI/Menu.PNG` / `Map.PNG` / `EdMenu.png`); nothing else inside a
  `romfs/` is looked at (`_icon_walk()`). `EdMenu` / `Ed Menu` is the Results icon, not a second Menu.
  **Colour packs** (`_colour_pack()`, Fall Guys): pictures named by colour - `Map Light Blue.png`, `Menu Black.png`, `Ed Menu Pink.png`,
  in any folders - for a character whose icons come in colours. The colour name is matched to the game's own slot for it
  (`COLOUR_WORDS`). That order differs per character and was read off the game's own icon textures (`COLOUR_SLOT_NAMES`):
  Yoshi green, red, dark blue, light blue, yellow, pink, black, white, orange; Shy Guy red, green, blue, light blue, yellow, pink, black,
  white, orange; Birdo (named by her body, the bow is another colour) pink, red, blue, light blue, yellow, green, black, white, orange;
  Inkling Boy blue, purple, teal; Inkling Girl orange, lime, pink. Only words that mean one slot are listed ("blue"/"navy" = the dark blue,
  "cyan"/"aqua"/"sky blue" = the light blue; Shy Guy's "grey"/"silver" = his white). One colour the game has no slot for ("Purple" for Yoshi)
  takes the single slot left over - so Fall Guys' Purple goes to Yoshi's dark blue slot, a reasonable reading but not something the files
  prove; two or more such colours, or a name that could be two slots (Birdo's "Purple": her blue or...), are left out rather than guessed.
  The set's pictures carry the slot's name (`Yoshi02`), so they reach exactly that colour.
  **Numbered colours** (`_numbered_colours()`, Shy Guy Ninja's `tc_Chara_shy0.png` .. `shy8.png`, results `shy0k.png`, map `shy0kk.png`): a
  name the game doesn't have, with a number in it, is that colour's own picture when the numbers of a kind are exactly the character's colours -
  0..n-1 (the game's slot numbers) or 1..n. Checked on Shy Guy Ninja against the game's own icons: shy0..shy8 are slots 00..08. Fewer, or a gap:
  left alone (they would all go to every colour, and the last would win). One-colour characters keep their made-up names.
* Small pictures are kept at their exact size (a 64x64 map icon is
  byte-identical in the built file). An icon the base file doesn't have (a
  character added in a newer game version than the base copy) is listed as
  "can't be added" like any other.

**Colour-variant characters.** The game keeps one icon texture per *colour* for Yoshi
(`Yoshi00..08`), Shy Guy (`Heyho00..08`), Birdo (`Catherine00..08`) and the Inklings
(`SplatoonBoy00..02`, `SplatoonGirl00..02`) and has no plain `Yoshi`. `ui_setup.COLOR_VARIANTS`
records the counts; `slot_items()` gives every texture of a character's icon, and the Menu
look card treats them as one slot ("all 9 colours" / "8 of 9 colours"). A picture the user
supplies goes to every colour.

**Which texture a loose picture goes to** (`resolve_pictures()`): a picture named for a real
game texture (`tc_Chara_SplatoonGirl02^l`) goes exactly there; one named for something the
mod made up (`MarioSunshine`) or by purpose goes to all of the character's textures; one
named for a *different* game character (Vanellope UI's `BbRosetta` filed under Wendy) is
**not** applied automatically - the card says so, the pictures show up in Baby Rosalina's
Customize list ("filed under Wendy, but named for Baby Rosalina"), and "Use these for X
anyway" overrides the rule. Pictures named by purpose (`King Dedede Map.png`, `... Menu.png`,
`... Common.png` = map / select screen / results; at least two kinds, small images) form a
set too. UI-only downloads (a folder with no `romfs/` anywhere - a "UI icons" companion) can't
be ticked, so `gather_auto_icons()` considers them regardless of ticks.

**Icons a mod ships but that can't be applied** (a picture of another shape or format, an icon
the base file lacks) are shown as "can't apply" on the card with the reason, not as "from a mod".
A picture that is only a different size (Dr. Mario's 40x40 map icon vs the game's 64x64) is
scaled to fit (LANCZOS, alpha-safe, re-laid-out for the GPU like the base texture) and marked
"resized to fit" on the card and "resized from 40x40" in the guide; the build check
resizes the mod's picture the same way to compare.

**Long labels.** `mod_label()` shows a mod folder's unit name only when it adds something (a
re-spelling of the mod's own name doesn't), cuts the mod name to 40 characters and the unit to 32,
and the conflict card's tooltip carries the full names (`full_labels`).

**Adding many mods.** `get_unit_slots()` / `slot_characters()` read each unit's `Driver/*.szs`
and voice/menu-sound files (`DRIVER_SLOTS`: driver name -> character, verified against the
mods downloaded for each character; unknown ones such as Larry/Isabelle/Mii/Birdo/Diddy/Funky
Kong are never claimed) to badge a unit "replaces Donkey Kong" and warn at download time
(`_character_slot_mismatch()`, shown like the course/vehicle slot warnings). "Select All"
(per item and per Full List category) skips units that replace another character's slot and
ticks only one of several units that write exactly the same files (colour variants,
menu-sound options - the already-ticked one, else the first); "Deselect All" clears
everything. In the fetch card, a multi-file mod gets its most likely file pre-ticked
(`suggestFiles()`: newest / fullest / named for the item; not old, alternate or optional).
`gb_download_files()` fetches several files at once (`gamebanana_api.prefetch_files()`, 4
connections; GameBanana serves ~100-150 KB/s per connection) before the usual one-by-one
extract. The Menu look card offers "Use "Sandy Cheeks"" chips built from the mods' own names.

Caveat: "Unchanged" means no mod changes it relative to the *consensus* of your
mods' copies - if every copy already carries the same custom icon it counts as
unchanged and is what's shown.

## Voice editing: mute a line, or use your own sound

A character's card has a **Voice** row (**Edit voice lines**). Like **Name** and **Icons**, it is dimmed ("Comes after
you pick a mod", no Edit button) until the character has a ticked mod - `attachVoiceRow()`'s `setEnabled()`, fed by the card's `refresh()`.
The character's own *Custom voice* mod doesn't count toward that, so it can't keep the row open after the real mod is unticked
(existing edits aren't touched - the row just can't be opened until a mod is ticked again). The window lists the character's voice lines - the four
*important moments* first (character select, finish first, finish mid-pack, finish last), then every other line by category -
each with a short description, a play button, and **Mute** / **Use my own...**. A handful of lines say "Unknown" instead of
a description - nobody's traced what triggers them (checked against real Switch hardware, and two modder references - see
`voice_edit.LINES`'s header comment); play one to hear what it is rather than trust a guess dressed up as fact.

### What the game's voice files are (and what is proven)

* Each character has two archives: `romfs/Audio/DriverMenu/MenuDriver_<slot>.bars` (the character-select sound: one, sometimes
  two sounds) and `romfs/Audio/Driver/Driver_<slot>.bars` (73-82 sounds used during a race, horns included). `<slot>` is the
  game's own name for the character (`DRIVER_SLOTS` in `mod_manager.py`). A voice mod replaces a whole archive.
* An archive ("BARS") is a header, a table of name hashes, a table of offsets, one small metadata block (AMTA) per sound, then the
  sounds themselves (FWAV/BFWAV files), each starting on a 0x40 boundary. Names can share one sound's data (`START_GLIDE` and
  `START_GLIDE2`). All 1,959 sounds in the 60 archives of the author's mods are DSP-ADPCM (the format of every voice in the
  game), little-endian (one sound is big-endian), 1958 of them with no loop; 87 % mono; sample rates from 8 to 48 kHz (59 % at
  32 kHz); 0.005 to 6.7 seconds. Mods mix rates and lengths freely, so a new sound does not have to match the one it replaces.
* **Proven on a real Switch** (hand-built test mods, `audio-test-mods/`): swapping chosen sounds of a real archive for a tiny
  silent sound works in both kinds of archive - other sounds are untouched, and the metadata blocks need no change (mods that
  work on the Switch leave them as they were, even when a sound is replaced by 0.005 s of silence). The silent sound used is a
  copy, byte for byte, of the one in a mod known to work.
* **Finish sounds** (heard on the Switch): `GOL_TOP` plays when you finish first, `GOL_GOD` mid-pack (heard at 4th), `GOL_BAD` at
  the end (heard at last). Each is three sounds: the plain one, a `2` variant and an `_END` tail; which of the three plays when
  is not known, so a line is always changed as a whole.
* **Also proven on a real Switch**: a custom sound made by `voice_dsp.py` plays correctly, in both a race line and a menu
  select sound, in full, with the rest of the character's voice and the rest of the game unaffected (tests 3-4 in
  `audio-test-mods/`). **Not proven**: lines longer than 6.7 seconds (the app limits a line to 8; test 5, skipped so far).

### How it works

* A **line** is what a player thinks of as one thing the character says. In the archive it is one or more sounds; the line's
  key is the sound's name without the character's code and without the number / `_END` (`pVO_BMR_GOL_TOP_END` -> `GOL_TOP`;
  menu sounds are `M_SELECT_CHAR`; horns `HORN_ON` / `HORN_OFF` / `HORN_ON_SP`). `voice_edit.LINES` holds each line's label,
  description, and how sure the description is (`sure` - heard on a Switch or plainly said by the name; `likely` - the name
  and the game make it clear, or an outside source backs it up; `unknown` - no source or reading pins it down, so the
  description just says "Unknown" instead of a dressed-up guess). Any sound the list doesn't recognise at all gets the same
  treatment - a plain "not identified yet" description rather than being hidden.
* **Muting** swaps every sound of the line for the silent sound. **Use my own** takes an audio file the user chooses: the *page*
  reads it (`decodeAudioData` - mp3, wav, ogg, m4a, flac..., whatever the browser plays - brought to 32 kHz), shows it as a
  waveform to pick the part (drag, or start/end), can cut the quiet ends, previews it, and sends the 16-bit samples; the app
  keeps them as a `.wav` in `voice-custom/<character>/` and encodes them into the sounds of the line: the same channel count
  as each sound it replaces (mono is doubled, stereo averaged), rate kept as sent. Up to 8 seconds.
* **Loudness.** The author's real race lines measure a median -14.7 dBFS (RMS) with a crest factor (peak / average) around 4.7 -
  compressed, "mastered" audio. Plain speech has a crest factor of 10-17 (quiet most of the time, brief loud syllables), so simply
  raising a recording's *peak* to just under full scale (the first version of this) left it 9-11 dB quieter on average than the
  game's own voice - confirmed on a Switch ("a bit too quiet" / "almost too quiet to hear over the music"). "Match the game's own
  voice volume" (on by default) instead: a soft compressor brings the crest factor down near the game's, then a gain is searched
  for (the limiter that follows would eat into a single-shot guess) to bring the *result* to that -14.7 dBFS target, then a smooth
  (tanh) limiter catches any remaining peaks by bending them toward the ceiling rather than flattening them (`matchGameLoudness()`
  in `src/ui/js/voice.js`; checked afterward: well under 1% of samples in the processed test audio come near the ceiling, and the
  encoder's accuracy is unaffected). Unticked, the audio is used as decoded, unprocessed.
* **The starting archive.** Changing one line means writing the whole archive again, so the app needs the archive as the game
  would otherwise use it: the copy in a *ticked* voice mod for that slot (that is what the game would play; one left out of the
  merge is skipped), else the app's own base-game-files copy (`game_files.find_current_voice()` - see "Base game files" above;
  required since Setup, so this is now the normal case for a character with no voice mod ticked). With neither - a character
  whose `DRIVER_SLOTS` code isn't known, or a base-files copy that's somehow missing - the editor says so plainly rather than
  guessing.
* **The Custom voice mod.** The result is an ordinary mod, `mods/extracted/characters/<Character>/Custom voice/romfs/Audio/...`
  (only the archives that have an edit), ticked when it is first made and merged by Commit like any mod. Its tick is the
  user's: unticking it turns the edits off without losing them.
* **The mod it was made from** would clash with the Custom voice mod on the same file, so while the Custom voice mod is ticked the
  app leaves that mod's copy of the file out of the merge (an ordinary left-out file, `kept_from` = the Custom voice mod, visible
  in its Files list) and puts it back when the Custom voice mod is unticked, removed, or has no edits left. Only the archives the
  Custom voice mod actually writes are left out.
* **When the starting archive changes** - another voice mod is ticked or this one unticked, the game folder is set or cleared -
  `sync_voice_edits()` writes the archive again from the new base (custom lines are encoded again from the saved audio). It runs
  when ticks are saved, the mod list is loaded, a mod is removed, before a commit, and when the editor opens; it does nothing (and
  costs nothing) when there are no edits. If there is no starting archive any more the edits are **kept but paused** - the Custom
  voice mod is put away (it would otherwise keep playing the old mod's voice) and comes back by itself when a base is back.
* **Commit** picks the Custom voice mod's archives up like any other file; the commit signature includes the voice edits (only
  when there are some, so an earlier commit is not called stale), so changing a line makes the last commit stale.
* A muted **select sound** is not a sound to play: the tile's click plays nothing and its tooltip says nothing about it
  (`get_select_voice` / `_select_voice_source` treat a sound shorter than 0.05 s as silent).
* The Api calls take turns (a lock), because the window can call from several threads at once.

### Encoding (`voice_dsp.py`)

DSP-ADPCM is 4 bits a sample in 8-byte frames of 14 samples: a header byte (predictor number, scale) and 7 bytes of nibbles.
The encoder works out a good predictor pair for every frame, groups the frames into the eight predictors a sound may carry,
then for each frame tries the two best predictors at the finest scale at which every value still fits, following the decoder's
own integer arithmetic sample by sample. Silence stays silence. A few seconds encode in well under a second (pure Python).
The `.bfwav` written is laid out exactly like the game's own: `make_fwav()` of a silent stereo 48 kHz sound is byte for byte the
silent sound of a working mod, and for real mono and stereo sounds of several sizes every header, INFO and padding byte comes out
identical to the real file (only the coefficients and the audio differ). Real speech comes back at 38-43 dB signal-to-noise,
a game voice line decoded and encoded again at 41 dB.

### Tests

`p28` (archive rewriting on all 60 real archives, line grouping), `p29` (muting through the Api), `p30` (the encoder and
layout), `p31` (custom audio through the Api), `p32` (everything on a read-only copy of the author's real data: no new clashes,
a tick with edits present takes 0.2 s, the real folder byte-for-byte untouched), `p33` (commit staleness, concurrent clicks).

## Code patches (exefs `.ips`), not just romfs

Some mods - most of the **Mechanics** category (a coin cap, a version
backport, ...) - change no romfs data at all; they ship IPS patches for the
game's executable, one file per game build, named after its build id
(`<32 hex chars>.ips`). These are first-class mergeable units:

- **Discovery** (`find_exefs_units()`): any folder outside a `romfs/` that
  directly holds a `<hex>.ips` file - the mod's own `exefs/` (Ryujinx-style
  layout, which is what most mods ship), `exefs/<name>/`, or an author-shipped
  `atmosphere/exefs_patches/<name>/`. The unit key is that folder's path. A
  mod with both a romfs and a patch gets two separate units, so the patch is
  always its own deliberate tick ("Select All" skips patches).
- **Staging** (`Api.merge()`): each checked patch unit is copied to
  `sd-card-staging/atmosphere/exefs_patches/mk8dxmm_<mod name>_<hash>/<BUILD ID>.ips`
  (upper-case build id, lower-case `.ips`). This is Atmosphere's own layout -
  the loader scans every set under `atmosphere/exefs_patches/`, applies only
  files whose name matches the running game's build id, and stacks patches from
  several sets. It ignores `.ips32`, `.pchtxt`, `.IPS` and non-hex names, so
  those are never staged (the log says when one was ignored). The
  `mk8dxmm_` prefix is what lets a re-merge delete exactly its own previous
  patch sets without touching sigpatches or anything else already on the SD.
- **Conflicts** (`_compute_exefs()`): both patch formats (`PATCH`/`EOF` and
  `IPS32`/`EEOF`, RLE records included) are parsed, and two checked patches
  for the same build id that write *different* bytes to an overlapping range
  conflict, reported with the pseudo-path `exefs/<build id>@0x<offset>`.
  Identical bytes are fine. There's no saved-preference resolution for these
  (half a patch can't be dropped) - one has to be unchecked. What this can't
  see is *logical* incompatibility between patches that touch different bytes.
- **Game version**: a patch built for a different build does nothing, with no
  error. `KNOWN_BUILD_IDS` maps the ids whose version is confirmed (deliberately
  short - unknown ids just show their raw id), and the optional "Game build ID"
  in Settings flags patches that don't target the user's own build ("wrong game
  version" badge + a merge-log warning).

Course mods that ship their own exefs patch (e.g. a music-related one) used
to have it silently dropped by the merge; it now shows up as its own unchecked
"code patch" unit next to the course's romfs unit.

## Vehicle parts: bodies, wheels, gliders

The **Vehicles** tab has three sections - Vehicles (41 bodies, split into
karts / bikes / ATVs), Wheels (22 tires) and Gliders (15) - each a fixed roster
from `src/roster.json` (name, internal id, aliases; researched against the
wiki, mk8dxbuilder.com and real mod archives, unchanged through game 4.0.0).

**The screen** works like Character Select and Course Select: the three sections are boards, every part is the game's own
picture of it (no name on the tile), and it is sized to fit the window without scrolling. The part being viewed - the one
whose card is (or was last) open - has the yellow corner brackets and its name on the plate along the bottom, with its kind
small beside it ("Mach 8 (Kart)"); while the mouse is over a tile, the plate shows that one instead and a white frame follows
the mouse. Tick counts (a pack counts on every tile it is listed on - see "A mod for something other than its card") and the red conflict "!" are as before; a hovered tile gets only the white frame (no accent border).

Fitting (`fitVehicleScreen()` in `js/vehicle-screen.js`): one tile size for all 78 parts (a 200:128 picture), found by
trying every size from big to small and every way of laying the boards out - `a` [bodies | wheels over gliders], `b` [bodies
over (wheels | gliders)], `c` [bodies | wheels | gliders] - with every count of tiles per row for each board; the first size
at which one fits wins, and of the fits at that size the one that takes the least room. The sizes it counts with (a board's
padding, heading and sub-headings) are the CSS's own, so the prediction is exact; a board is never narrower than its heading
text, which is measured once. Only a window too small for even 36 px tiles scrolls. `css/vehicle-screen.css` comes last.

**The pictures** (`vehicle_icons.py`, `Api.get_vehicle_icons()`): every one is a 200x128 RGBA texture named
`tc_KP_<kind>_<part>^l` (K kart, B bike, V ATV, T tire, G glider; `<part>` is the roster's own internal id - `BodyK_Ufo` ->
`K_Ufo`, `Wing_Wlo` -> `G_Wlo`, a tire's `Std` -> `T_Std`). Most (62 parts) are one texture inside `menu.sarc` ->
`mn_L_KartParts_00.szs`. The 16 families that come in outfits - the Standard Kart, Standard Bike, Pipe Frame, Standard ATV
and Super Glider once per character, the rest numbered - are **351 loose files** in `UI/cmn/menu/` (each 110,696 bytes, one
texture, its internal name equal to its file name); the screen shows each family's default (Mario's red, or `_00`). Master
Cycle's picture is `B_Zld` (its roster id spells it `Zlb`). Every mapping was checked by looking at the decoded pictures.
Before Setup - or if a picture is missing - the tile shows the part's name.

**The card** is guided like the character and course cards: a head with the part's picture, its name, its kind and where it
stands ("Kart · 2 mods in use"), and a chip (No mod yet / Choose a mod / Needs a look / Done); then the mods in use (the
rest behind "Manage"), with "Find a mod" / "Add another mod" under them (packs that replace this part are ordinary rows here);
then three steps:
- **Right part** - a mod is filed under a part by where it was found, but what counts is the model file it ships: a ticked
  mod whose file is for a *different* part changes nothing on this one, so the step says which part it is really for and
  offers "Move it to <part>" (`gb_move_mod()`, which takes the tick with it) or "Untick it". Worked out from the files
  (`Api.get_vehicle_fit()`, reusing `_vehicle_slot_mismatch()`), so nothing is confirmed or remembered, and it is not part
  of "finished". (`gb_move_mod` callers reload the ticked state too - the move renames the mod's key, and a stale one would
  have been written back.)
- **Name** and **Icons** - the same two steps as a course, confirmed per set of ticked mods and remembered
  (`look-reviews.json` buckets `part_names` / `part_icons`; `Api.get_part_look()`, `confirm_part_name()`,
  `mark_part_icon_reviewed()`). Vehicle parts count in the "N aren't finished" prompt and the review queue.

Each section is its own on-disk category (`vehicles/`, `wheels/`, `gliders/`),
nested `<category>/<part>/<mod>` like everything else, and reuses the
character modal / GameBanana card / conflict machinery unchanged.

- **GameBanana has no per-part subcategory**, only section categories under
  Vehicles (10530): bodies by type - Kart 10571, Bikes (Outward = standard)
  10572, Bikes (Inward = sport) 10573, ATVs 10574 - Tires 10577, Gliders 10578
  (`Api._vehicle_gb_category_id()`). Browsing a part lists every mod of its
  *kind* (`gb_browse_vehicle()`), starting on Most Viewed (until the user picks another sort, which is then remembered) because
  GameBanana's "Most Liked" paging repeats/skips mods in these large
  categories - the window drops the repeats. Roughly 4% of body mods are misfiled under the wrong subcategory,
  and some tire/glider mods sit directly in Vehicles with no subcategory.
- **Which part a mod replaces is read from its text**, not its category
  (`match_vehicle_targets()`): an internal id (`BodyK_Cat`, `Wing_Pap`,
  `TireK_Zst`) beats an "over / replaces <name>" phrase, which beats a bare
  mention; single common words (Standard, Metal, Comet, ...) never count as a
  plain mention. Measured against real archives, "goes over" phrases agree with
  the files ~98% of the time when present; titles alone are unreliable. The
  listing has no descriptions, so each browsed batch fetches its mods' profiles
  (3 at a time, cached - GameBanana rate-limits bursts with HTTP 429) and tiles
  get a "Replaces X" / "Mentions X" badge plus an "only likely matches"
  filter, on by default (for items too, except the "Other items" tile). The list keeps loading until enough likely ones
  fill the window; after two batches in a row with none it pauses and offers "Keep searching" / "Show every mod". It's a
  guess, never a filter you can't turn off.
- **The downloaded files are the real check**: the model files a mod ships
  (`Kart/Body/BodyK_*.szs`, `Kart/Tire/TireK_*.szs`, `Kart/Wing/Wing_*.szs`)
  name the exact part they replace, so a download whose files don't include the
  part it was filed under gets the same "slot mismatch" warning courses do
  (`find_vehicle_part_ids()`). That includes a different *kind* of part: a tire or glider mod filed under a body, say (a mod
  with no model file at all, such as a texture pack, is never flagged).
- **Loose files are auto-wrapped**: about half of body mods ship
  `BodyK_Cat.szs` etc. with no folders at all; `fix_loose_kart_parts()` moves
  each into `romfs/Kart/<Body|BodyTex|Tire|Wing|WingTex|Emblem>/` by its file
  name, all-or-nothing like the loose item-file fixer.
- The **Add a mod** flow can suggest a vehicle part from the mod's category +
  description.
- **Packs and misfiled mods** (a character mod that also ships a body, a body mod filed under the wrong part...) are handled
  the same way for every kind of thing - see "A mod for something other than its card". Only the real load locations count
  for a vehicle part (`romfs/Kart/{Body,Tire,Wing}/`); per-character paint (`BodyTex`/`WingTex`) and `Emblem` files don't, since
  those are a character's own colors on a stock part, not a replacement of it.
- **Add a mod**: a mod that's unmistakably a vehicle part but whose text names
  no part (`guess_category == "vehicle_unsorted"`, typically filed directly
  under GameBanana's Vehicles) opens with "- pick a part -" selected instead of
  an arbitrary default. The roster carries common alternate spellings as
  aliases (e.g. "Sneaker" for Sneeker, which real mods use).
- **Multi-file mods, one step**: plenty of vehicle mods bundle files that each
  belong under a *different* part - one download per glider/kart ("Streetle
  Ver" / "Prancer Ver"), or a companion tires file next to the body. For a
  vehicle mod with more than one file, Add a mod shows a per-file part picker,
  prefilled by `suggest_file_targets()`: the file's own name/caption first
  (GameBanana's random 5-hex upload suffix and separators stripped), then, for
  a file that names nothing itself, the mod's text restricted to the kind of
  part the file is (so a `tires_....zip` file resolves "...tires replace Wood"
  to Wood). By default every file that names its own part is ticked, plus only
  the first file per part that merely inherits the mod's target (a second one
  is normally an alternative variant, not something to download too). An
  optional **icons companion** (`ui-...`/"icons" file - UI art the app can't
  merge) is never the default when a real mod file covers the part, is labelled
  as such, shows as fine rather than a warning in the summary, and doesn't
  stop the real file from being auto-ticked (`is_companion_file()`). "Add this
  mod" then files each group under its part and downloads it in one call
  (`gb_add_vehicle_mod_files()`), so all the usual safeguards still run, and a
  summary lists each file's outcome - with a **Move to** button for any whose
  real part differs. A part that ends up with exactly one clean mod is ticked,
  as after a single download. Untick "File each file under its own part" for
  the old single-target flow.
- **Wrong game**: GameBanana keeps "Mario Kart 8" (Wii U, game 5709) and
  "Mario Kart 8 Deluxe" (Switch, 6507) as separate games with parallel category
  trees (the Wii U vehicle tree is category 7442, ~600 mods, not included in
  browsing). A pasted link to a Wii U mod is flagged in the Add a mod dialog and
  on its card (`game_id` is stored with every fetched mod) - it very likely
  won't load on a Switch. Re-fetching a mod also keeps its recorded slot
  warnings and archive location now (it used to drop them).

## Items

**Items** has its own tab (it used to be a row on the More tab, one fixed pseudo-item with a plain list). It is a fixed roster from
`src/roster.json`'s `"items"` - 22 items (Banana, Green Shell, Red Shell, Spiny Shell, Bob-omb, Mushroom, Golden Mushroom, Super
Star, Lightning, Boomerang Flower, Fire Flower, Piranha Plant, Bullet Bill, Blooper, Boo, Super Horn, Crazy Eight, Feather, Coin,
Rupee, Bell, Item Box) plus a last tile, **Other items**. Each entry has a `name`, `aliases`, an optional `internal` (the model
folder under `RaceCommon/Item/`, e.g. `ItemKoura` - left out where two items share one, the Green and Red Shell, which are both in
`ItemKoura.bfres`) and an optional `icon`.

**The pictures** (`item_icons.py`, `Api.get_item_icons()`): 19 of the 22 have a 192x192 RGBA texture `tc_Item_<icon>^l` in
`menu.sarc` -> `mn_L_ItemSwitch_Item_00.szs` (the Item Switch screen of a custom race: `Koura` = Green Shell, `PKinoko` = Golden
Mushroom, `SP8` = Crazy Eight ...), so nothing new is copied into the base-game copy. The same textures are in `race.sarc`
(`rc_L_ItemBox_00.szs`, the race HUD's item slot, along with the double / triple forms and the Rupee's), which the copy doesn't
have. The Item Box, Rupee and Bell are models only, so their tiles keep their name. Every picture was checked by looking at it.

**The screen** is laid out like Character Select: on a wide window (`DOCK_MIN_WIDTH`, 1100 px) the board is the left 55% and the
picked item's card is docked on the right, always with an item in it (the last viewed, else the first with a mod); on a small
one the board takes the width and the card is a pop-up, and resizing across the threshold moves an open card between the two
(`js/item-screen.js`; `beginDetail()` / `endDetail()` / `wantsDock()` in `character-select-layout.js` hand the card to the Items
view when it is showing). The name plate along the bottom shows the viewed item - or the one under the mouse, with a white
frame following - and how its mods stand. Nothing scrolls: `fitItemGrid()` takes the biggest square tile at which the whole
grid fits its board, over whichever number of columns gives the biggest (the count isn't tied to the game's 8), capped at 150 px;
`css/item-screen.css` comes after `vehicle-screen.css`.

**Mods and GameBanana.** Mods are filed under `mods/extracted/items/<item name>/<mod name>/`. GameBanana has one flat Items category
(10579), so - like tires and gliders - browsing it lists every item mod and marks each with the item its text says it replaces
(`gb_browse_item()`, reusing `match_vehicle_targets()` with the roster's names, aliases and model-folder ids; common one-word names
like "star" or "coin" only count after a "replaces / goes over" phrase). "Add a mod" has an **Item** target, prefilled from the
same guess; a mod naming no single item (or several: an item pack) is suggested for **Other items**. A mod that lands under the
wrong item, or in Other items, is moved from the mod's "..." menu like any other (see "A mod for something other than its card"; "Other items"
also lists its mods with a picker each). What was filed before items had a roster sits in `items/Items/` (the old
fixed pseudo-item): it isn't moved - the catch-all tile (name `Items`, shown as "Other items") collects it, along with anything in
a folder that matches no item.

An item mod's files say which item it replaces: the folders under `RaceCommon/Item/` (`ItemBanana`, `ItemPowerKinoko`, ...), matched to
the roster's `internal` ids (`_item_folder_owners()`; a folder that only extends an item - `ItemKoura_FX`, `ItemBomheiBomb`, `ItemCoinB`
- belongs to the longest id it starts with, and the Green and Red Shell share `ItemKoura`, so a mod shipping it replaces both).
Folders the app can't place (`ItemCommon`, which every item uses) leave the mod where it is.

Not done for items (unlike vehicle parts): the **Name and Icons steps** - an item's picture (`tc_Item_*`, in both `menu.sarc` and
`race.sarc`) has no override yet, and where the game's text names the items hasn't been found.

## Vehicle parts: names and pictures in the menus

The user has the same control over a part's UI as over a character's: its **name** and its **picture in the parts menu**, from
a mod or from themselves.

**Names.** All 78 part names are entries in `Common.msbt` (bodies 1101-1186, tires 1201-1222, gliders 1251-1265; one label
each, none shared), so they go through the same pipeline as characters and courses: `name-labels.json` has `vehicles`,
`wheels` and `gliders` sections, `ui_setup.NAME_LABEL_RANGES` the three kinds, `set_item_name(part, kind, text)` stores the
wish by name, and the text is written into every language's `message.sarc` at commit. A mod's own text is read the same way
(`get_menu_look()`), and a name can be guessed from the mod's name, which is only a suggestion until confirmed.

**Pictures.** The picture source is one of, in this order: what the user chose, what a ticked mod brings, the game's own.
- A part whose picture is a texture in `menu.sarc` (62 parts): a chosen picture is a texture override
  (`mn_L_KartParts_00.szs|tc_KP_K_Ufo^l` in `ui-overrides.json`) and goes through the same build as a character's icon
  (`apply_overrides()` -> `menu.sarc`, checked by `verify_archive()`). A mod's own is found by the same diff of packed archives
  (`describe_texture()` names a part texture after its part, so it is attributed to the right one).
- A part whose picture is loose files (16 families, 351 files): a chosen picture is stored once (`loose|K_Std`), and
  `ui_setup.build_part_pictures()` writes **every variant file** of the family into `part-icons/romfs/UI/cmn/menu/` (always
  merged in, like `course-icons/`) - each the game's own file from the base copy with the picture swapped in place (the file
  keeps its name, size and layout; re-encoding the game's own picture reproduces it byte for byte). `Api.sync_part_pictures()`
  runs when a picture is set or cleared and at the start of every commit, and deletes files no longer wanted. A mod's own
  loose files count as its picture when the mod is filed under that part.
- **Precedence:** a picture you chose replaces the files of a mod filed under the same part, but a ticked mod filed
  *elsewhere* that ships the same file - a character mod's per-outfit `tc_KP_K_Std_MroM` - keeps it (`left_to_mods`; the
  Icons step says how many).
- Pictures are cropped in the icon dialog ("part" mode, 200:128) from a mod screenshot or **a file from the user's computer**,
  stored at up to 400 px in their own shape, and a picture of another shape is fitted inside the part's (never stretched).

Not verified in a running game: that the console shows the loose files and the new names (only the built files and text
were decoded and compared) - try it in an emulator or on hardware.

## A mod for something other than its card: one experience for every kind

GameBanana files a mod where its author put it, and the files inside often say something else - a Luigi mod on Mario's page, a tire
mod on a kart's, a course retexture on the wrong course, an item pack. This works the same for characters, courses, vehicle parts
and items, and the app talks about what a mod *replaces* (never "slots" or "filing").

**What the files say** (`_download_slot_mismatch()` -> a mismatch dict with `targets`, the things the files are for, and
`unresolved`, how many of the files' ids the app can't place): a character's `Driver/` and `Audio/Driver*` files
(`slot_characters()`), a course's `Course/<id>/` folder (`_course_slot_mismatch()`), a vehicle part's `Kart/{Body,Tire,Wing}/`
model - across kinds too, so a tire mod on a kart's page counts - and an item's `RaceCommon/Item/<model>/` folder
(`_item_slot_mismatch()`). A mod with no such file (a texture pack) says nothing and is never moved.

**After a download** (`gb_download_files()` -> `_refile_mod()`): if every downloaded file's files are for something other than the
card it came from and the app can place all of them, the mod is moved there (`gb_move_mod()`): one thing -> that thing; several
(a pack) -> the first of them in the app's order (`_refile_rank()`), where it is filed, and it is listed on the others (below).
The page then runs `finishRefile()` (`js/refile.js`): the destination's card opens (pop-up or docked) with a note - *"X" replaces
Mach 8, not Standard Kart, so it is now under Mach 8* / *"X" is a pack: it replaces A and B...* - the mod is ticked when it is the
only one that card has (the rule for any fresh download), and the note has an **Undo** (`undoRefile()`: the same move back, and it
unticks what the app ticked). Nothing is guessed: a file that fits the card, or names something unrecognised, leaves the mod where
it is, with a warning that names what it replaces and a "Move to X" button (`buildFileRow()`); a move that fails (the mod is
already tracked under the target) says so on the card.

**Moving one by hand**: every mod's "..." menu has "Move to another character / course / part / item..." (`openMoveDialog()`),
enabled for mods that came through GameBanana (`get_mod_ids()`; a mod added by hand has no record to move). A mod can only move
between things of its own kind (a character to a character, a part to a part). "Other items" - where item mods that name no
single item pile up - also lists each of its mods with a picker.

**What a move moves** (`gb_move_mod()`): the extracted folders, the archives, the tracking entry, the ticks, and everything else
the app remembers by the mod's path - the files left out of it, the clash priorities, voice edits, look reviews and menu picture
choices (`_rekey_unit_prefix()` rewrites those files). It returns `moved_folders`, which is how an undo finds the ticks. A failed
move is rolled back with nothing recorded.

**Packs** (`get_pack_links()`): a mod whose files replace more than one thing is listed on the card of each one. The pack stays one
mod filed in one place (never copied); its keys join the other entries' `units` on the page (`refreshViewsState()`, `packUnits`
marks them), so it is an ordinary row there - counted in the card and on the tile, in the footer totals (`get_stats()`), and in
conflict checks - with a "Pack . also X" badge (`buildPackBadge()`; click it to open the next card), and its menu says "Open where
it's filed" instead of "Move". One tick is shared everywhere, so ticking it on any card turns on everything in it, and the badge
and note say so. Wording is deliberately "replaces", read from the files: authors sometimes bundle stock files unchanged, and there
is no vanilla copy to compare against. This replaces the old vehicle-only, read-only "Also ships this part" card.

## Course-select icon preview & generation

The Course Select strip shows each checked course mod's actual in-game
select-screen picture (its `ym_CoursePict_<internal id>.bntx`, if it has
one) inline, so it's obvious at a glance which courses do or don't have
one - not just a guess from file names.

**Decoding** (`bntx_decode.py`) parses the `.bntx` header itself, undoes the
Switch's block-linear GPU texture tiling (the documented Tegra X1 GOB
addressing scheme), and hands the actual BC7 block decompression off to
Pillow's own DDS reader rather than reimplementing it - BC7 is one of the
fiddlier block formats to get exactly right by hand, and Pillow already
ships a tested decoder for it.

**Generating** an icon for a course whose mod doesn't bundle one ("Icon
from screenshot" on that mod's card, using its own GameBanana screenshots)
works the other direction (`bntx_encode.py`): the chosen screenshot is
cropped and composited into the fixed 304x256 canvas and written as a
plain **RGBA8** texture, not BC7 - deliberately, since that avoids needing
a BC7
*encoder* (a much harder, lossy problem than the decoder), and RGBA8 is a
standard, universally-supported baseline GPU format; the only real cost is
a larger file (roughly 300KB instead of 80KB) for one UI image, which is
immaterial. Rather than building a new `.bntx` container's string table/
name-lookup tree/relocation table from scratch, the generator loads a real,
already-working `CoursePict.bntx` from any of your own downloaded course
mods (via the vendored `_bntx_structs.py`, unmodified from
[BNTX-Editor](https://github.com/aboood40091/BNTX-Editor), GPL - see that
file's own docstring for why it's left unmodified rather than
hand-transcribed) and mutates only the handful of fields that actually
need to change - everything else keeps the exact structure a real, working
file already has. Generated icons live in `course-icons/` (see above),
never inside the mod's own downloaded folder, so they survive a
re-download/update of that mod and are easy to tell apart from what the
mod itself actually shipped.

**The 304x256 texture isn't fully "visible" picture** - every real
mod-provided CoursePict checked (four different mods, different authors)
leaves a near-identical black border baked into the raw file: an 8px
margin on each side, 29px on top, and 65px on the bottom, framing a
288x162 (exactly 16:9) visible window. That's not per-author styling
(the numbers land within 1px of each other across completely unrelated
mods) - it's the real template, and the lopsided bottom margin is almost
certainly reserved for the course name/mode text the game's own UI draws
over this texture at render time. `generate_course_icon()`
(`_COURSE_PICT_CONTENT_*` in `mod_manager.py`) composites into that exact
same window rather than filling the full canvas, and the crop tool's
aspect ratio (`ICON_GEN_COURSE_ASPECT` in `src/ui/js/help-and-icon-generator.js`) targets that 16:9 content
window directly - a typical 16:9 screenshot needs no letterboxing at all
before the app adds the matching border around it.

This can't be verified on real hardware from here, only structurally (the
generator's own round-trip: write, then re-parse and confirm every field
matches what was intended) - which is exactly why it's built on a real
file's proven structure rather than one built from scratch.

## Folder naming: nested by item, not flat "item - mod name"

Every download (both `mods/downloads/` and `mods/extracted/`) is organized
as `<category>/<item>/<mod name>`, e.g. `extracted/characters/Waluigi/Donald
Trump/romfs/...`, rather than the old flat `extracted/characters/Waluigi -
Donald Trump/`. This matters most for an item with several separate mods
(several Waluigi skins, say) - they now sit together under one `Waluigi/`
folder instead of as a wall of similarly-prefixed sibling folders, making it
much faster to find everything for one character/course by eye in Explorer.

Existing downloads from before this change are migrated automatically, in
place, the first time the app starts (or the master directory is switched) -
`Api._migrate_flat_mod_folders()` in `mod_manager.py`. It's driven primarily
by `gamebanana-mods.json`, which already knows exactly which item and mod
each downloaded archive/extracted folder belongs to, and only falls back to
guessing from a folder's name (matched against an exact `"<item> - "` prefix
from the roster) for anything not tracked there - a mod placed by hand,
outside the GameBanana flow. It's safe to re-run (every subsequent launch
does run it again) - once a folder is nested, its path no longer matches the
old flat shape, so there's nothing left for it to do.
