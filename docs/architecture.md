# Architecture: where things live

The backend modules, every file the app keeps in the master folder, how the frontend is organised, and how mods are laid out on disk.

## Where things live

- `src/mod_manager.py` - backend (a pywebview JS-API bridge; almost all of the
  actual logic lives here)
- `src/ui/` - the frontend (plain HTML, CSS and JS; no build step) - see "Frontend file layout" below
- `src/voice_audio.py` / `voice_edit.py` / `voice_dsp.py` / `voice_api.py` - character voices. `voice_audio.py` reads a voice archive
  (`.bars`) and decodes its sounds so the app can play them; `voice_edit.py` rewrites an archive with some sounds swapped
  (and knows what each voice line is called); `voice_dsp.py` turns audio into the game's sound format; `voice_api.py` is the
  Api's side of it (the Custom voice mod, where the starting archive comes from) - see [Voice editing](voice-editing.md#voice-editing-mute-a-line-or-use-your-own-sound).
- `mod-notes.json` - the user's own notes on mods - see [Notes on mods](mod-notes.md).
- A shared mod list (Export / Import in Settings) is a file the user chooses, never kept here - see [Sharing your mod list](mod-list.md).
- `voice-edits.json` / `voice-custom/` - what you muted or replaced per character, and the audio you chose for the
  replaced lines (kept so a line can be encoded again if the archive it goes into changes). Both auto-generated.
- `src/game_files.py` - the app's own local copy of the base game's files (menu icons/text, every character's default
  voice) - see [Base game files](base-game-files.md#base-game-files-a-required-local-copy).
- `game-files/original/` / `game-files/current/` / `game-files/manifest.json` - that copy. Auto-generated by the
  required Setup step; `original/` is never touched again after it's written, `current/` is what every other part of
  the app reads.
- `src/gamebanana_api.py` - the GameBanana API client
- `src/cup_icons.py` - reads the game's own Grand Prix medallions out of the app's copy of `menu.sarc` for Course Select -
  see [Course Select](course-select.md#course-select-the-games-prix-sized-to-fit).
- `src/vehicle_icons.py` - the same for the game's own pictures of every vehicle part, for the Vehicles screen - see [Vehicle
  parts](vehicle-parts-and-items.md#vehicle-parts-bodies-wheels-gliders).
- `src/item_icons.py` - and for the game's own pictures of every item, for the Items screen - see [Items](vehicle-parts-and-items.md#items).
- Caches - `src/image_cache.py`, `src/library_cache.py`, `src/gb_desc_cache.py`, `image-cache/`, `ui-setup-cache.json`,
  `gamebanana-descriptions.json`: all rebuilt on demand and safe to delete - see [caching-and-performance.md](caching-and-performance.md).
- `src/bntx_decode.py` - decodes a course mod's own `ym_CoursePict_*.bntx`
  select-screen thumbnail (a Switch BC7 or RGBA8 texture) to PNG, for the
  inline preview in Course Select - see its own docstring for exactly what
  it does and doesn't handle. Needs `Pillow` (see `requirements.txt`) for
  the actual BC7 decompression.
- `src/bntx_encode.py` / `_bntx_structs.py` - the write side: generates a new
  `ym_CoursePict_*.bntx` from a mod's own GameBanana screenshot when it
  doesn't bundle its own icon - see [Course-select icon preview &
  generation](course-select.md#course-select-icon-preview--generation).
- `src/roster.json` - the full roster: every character and course (courses
  grouped into their 24 cups) plus every vehicle part (bodies, wheels,
  gliders - see [Vehicle parts](vehicle-parts-and-items.md#vehicle-parts-bodies-wheels-gliders)) and every item (see [Items](vehicle-parts-and-items.md#items)), used so every one shows up in the
  app even before anything's downloaded for it. Each course entry also
  carries its real internal `romfs/Course/<id>/` folder name (see [Reference data](base-game-files.md#reference-data-course-internal-names-and-music-ids)).
- `gamebanana-mods.json` / `mod-manager-state.json` - your tracked downloads
  and "Mods to merge" checkbox state (both auto-generated, no need to touch
  by hand). Every app-owned JSON file is written in one step (`src/safe_io.py`), and the ticks keep the previous good copy as
  `mod-manager-state.json.bak` - which is also what the app falls back to if the file itself is ever unreadable.
- `mods/downloads/<category>/<item>/` - raw downloaded archives, one folder
  per character/course
- `mods/extracted/<category>/<item>/<mod name>/romfs/...` - what those
  archives unpack to (what `discover_mods()`/`find_mod_units()` scan). A mod
  is nested under its item's own folder rather than named `<item> - <mod
  name>`, so e.g. every Waluigi mod sits together under `extracted/
  characters/Waluigi/` instead of as separate flat `Waluigi - ...` folders -
  this happens automatically (see "Folder naming" below).
- `ui-icons/` - the combined character-select icon set and menu text that
  **menu icons & text** builds for you, automatically, as part of every commit
  (`ui-icons/romfs/UI/cmn/common.sarc`, `menu.sarc`, `UI/<locale>/message.sarc`
  - see [Menu icons & text](menu-icons-and-text.md#menu-icons--text-combined-character-icons-and-coursecharacter-names)); a commit
  replaces those three files (keeping the old one in `ui-icons-backups/`). Any other file the user puts there themselves, such as
  a loose texture from the UI Icon Worklist, stays separate from the checklist. Always merged in.
- `sd-card-staging/` - what a commit builds, ready to copy onto the SD card (`atmosphere/contents/<title id>/romfs`, `atmosphere/exefs_patches/`).
  The recommended place is inside the data folder (so it moves with it); an install from before that keeps the folder it already has
  *next to* the data folder, shown as "Existing folder", until **Use the recommended folder** switches it. **Settings > Staging folder**
  (`staging_folder`: "" = the default, `@data` = inside the data folder whatever else exists, or a path; `Api._staging_dir()`) chooses another. Nothing is moved when it changes, and
  the last commit stops counting (its files are not in the new place). It is not asked in Setup.
- `ui-icons-backups/` - a timestamped copy of any file in `ui-icons/` that a
  build replaced or removed (never deleted automatically)
- `excluded-files.json` - files each mod must NOT contribute to a commit (how
  clashes are settled, and per-file choices from a mod's "Files" button - **Edit included files** in a character mod's **...** menu) - see
  [Conflicts: leaving files out](merge-rules.md#conflicts-leaving-files-out)
- `src/name-labels.json` - shipped reference data: which numeric text entry of the game's
  `Common.msbt` holds each character's (49) and course's (96, both the short and the
  cup-line entry) name - the numbers are the same in every language and every mod. Lets
  a name be handled without opening any game file, and lets the app tell when a mod's
  own text file already renames a character (its entry no longer matches the game's
  name). Villager (Boy)/(Girl) aren't listed (two identical "Villager" entries). Link (Breath of the Wild) has no entry of its
  own: the game has one "Link" text for both versions, so `ui_setup.NAME_ALIASES` gives it Link's (naming either names both).
- `ui-overrides.json` + `ui-overrides/*.png` - icons and names you supplied in
  a character/course popup's "Menu look" card - see [Menu look](menu-look.md#menu-look-your-own-icons-and-names)
- `look-reviews.json` - which characters' looks you have confirmed with "Looks right" (see [Checking a
  character's look](menu-look.md))
- `part-icons/` - the user's own pictures for vehicle parts that are loose files (see [Vehicle parts: names and pictures in
  the menus](vehicle-parts-and-items.md#vehicle-parts-names-and-pictures-in-the-menus)); the same idea, always merged in.
- `course-icons/` - app-generated course-select icons (see [Course-select
  icon preview & generation](course-select.md#course-select-icon-preview--generation)) - always merged in, same idea as
  `ui-icons/` but kept separate so generated files never mix with your own
  hand-curated icon work

For the day-to-day usage guide, see the app's own **Help** panel (top
right) - it covers the five-step flow, Menu Look, voice editing, conflicts,
the file-status glossary and known issues, and stays current with the UI
since it lives in the UI itself (the `helpModal` spec in `src/ui/js/app-modals.js`) rather than a separate doc.

## Fixing badly packaged downloads

`download_gb_file` runs a chain of fixers on a fresh download, each only while no mod unit (a folder with a `romfs/`) has been
found yet, and each all-or-nothing per folder (a folder with anything unfamiliar in it is left for manual review): the
missing-`romfs` wrapper (`Driver/`, `Kart/`, `Audio/`... found bare), bare course folders, loose item files, loose vehicle parts
([Vehicle parts](vehicle-parts-and-items.md)), and **loose character files** - `<Slot>.szs`, `Driver_<Slot>.bars` and
`MenuDriver_<Slot>.bars` (plus `Emblem_*.szs`) side by side with no folders, moved by name into `romfs/Driver`,
`romfs/Audio/Driver`, `romfs/Audio/DriverMenu` (`fix_loose_character_files()`). The slot must be one of `DRIVER_SLOTS`; a folder
mixing character files with vehicle parts is left alone.

Course mods have one more: **loose course files** (`fix_loose_course_files()`) - a "Retextured" mod that ships just
`course_model.szs` (and a README) with no folders, or inside a folder named for the mod. The download was made from a known course's
page, so the course names the folder: `roster.json`'s `internal` id (`Gu_SnowMountain` for Mount Wario, ...; all 99 exist in the
game's own `Course/` folder) gives `romfs/Course/<id>/`. Only for a course with one id (Animal Crossing's four seasons can't be told
apart), only when every file is one a course slot holds (`course*.*`, `*_muunt.byaml`, `enemy_path*.bin`, docs and pictures stay
put) with at least one of `course_model.szs` / `course_kcl.szs` / `course_muunt.byaml` / `course.bgenv` / `course_maptexture.bntx`,
and not for a folder already named for one of the game's course ids (`fix_bare_course_slot()` takes that one). It runs before
`fix_bare_course_slot()`, which would take a wrapper folder's own name for the id.

The **missing-`romfs` wrapper** fix also takes a bare `UI/` along when it holds the game's own `cmn/` folder and sits next to
`Audio/`, `Driver/`, `Kart/`... (a course's loose `UI/cmn/Menu/ym_CoursePict_*.bntx` picture, say) - alone, a folder called `UI` could
be a modder's own. And a `Menu` / `Common` folder inside `UI/cmn/` no longer makes a download look like a raw UI-archive dump
(`looks_like_ui_assets()`): that is where the game itself keeps those loose textures. Checked on "Mushroom Bridge V3" (Course + Audio
+ UI/cmn, now one mod) and "Triforce Mario Highway" (Daytime / Nighttime / Sunset now three mods; its shared `UI/` and `Music/` folders
beside them stay outside the `romfs/` folders). Fixers run at download time only, so an existing broken download is
fixed by downloading it again.

## Frontend file layout

The UI is plain HTML, CSS and JavaScript under `src/ui/` - no build step, no bundler, no modules. pywebview serves that folder
over its built-in local HTTP server (which is why relative links and `fetch()` work), so everything the page loads must live
under `src/ui/`.

- `index.html` - the page frame only: the header, tabs, the main views, the footer, and one `<link>` per stylesheet.
- `html/*.html` - the markup of the windows that are not built from specs (`add-mod-modal`, `gb-browse-modal`, `gb-detail-modal`,
  `icon-gen-modal`, `character-modal`, `setup-overlay`). `js/bootstrap.js` fetches them and adds them after the frame. All but the Setup
  overlay are adopted onto the window stack in `js/app-modals.js` (`ui.modal({ adopt })`), so they open, close, stack and take Escape like the rest.
  Settings, Conflicts, Help and Guessed names are not markup files at all: `js/app-modals.js` builds them from the components in `js/ui/`
  (`ui.modal`, `ui.section`, ...), which load first. See `docs/ui-components.md`.
- `css/*.css` - the styles, split along the old file's section comments. **Order matters**: later rules override earlier ones,
  so the `<link>` order in `index.html` is the cascade. Add a stylesheet after whatever it needs to override.
- `js/*.js` - the app. These are ordinary (non-module) scripts that share **one global scope**, run one after another in the
  order `SCRIPTS` lists in `js/bootstrap.js`: state and helpers first, then tiles, the character card, the views, add-a-mod,
  settings, the guided flow, and `main.js` (the `pywebviewready` handler that starts the app) near the end. Top-level code in a
  file may use anything an *earlier* file declared, but not a later one (a function declaration is only hoisted within its own
  file), so a new file goes where its dependencies are already loaded.

`bootstrap.js` also covers one timing trap: pywebview fires `pywebviewready` once, as soon as the page has loaded, which can be
before `main.js` has registered its listener now that the scripts load one by one. It notes the event and replays it once every
script is in.

Which file holds what, roughly: `tiles-and-review.js` (character/course tiles, the "have you checked the look" review),
`character-select-layout.js` (the docked card, hover name bar), `gamebanana.js` (the mod detail window and the GameBanana card), `refile.js` (a mod for something other than its card: the note, Undo, "Move to..."),
`gb-browse.js` (the Browse GameBanana window), `rich-text.js` (descriptions with links),
`voice.js` (playback, the voice editor, the "Use my own sound" tool, the card's Voice row), `character-card.js` (the card
itself and its Name / Icons walkthroughs), `help-and-icon-generator.js`, `views.js` (Full List, More, Course Select, tab switching; `renderAll()` draws the screen being looked at at once and the others one at a time a moment later), `api-coalesce.js` (identical read-only backend calls made at the same moment share one answer, and `conflictCount()` sends every tile's conflict question of one draw as a single `check_conflict_counts` call). A tick redraws only the screen it changed (`refreshBehindModal({ifChanged: true})`, see `viewSignature()` in `views.js`), bursts of refreshes are merged into one redraw, and the character icons and course pictures the page already holds are not sent again (`get_character_tile_view`'s `known_icons`, `courseDefaultPictures`; emptied by `resetPictureCaches()` when the game's files change), `vehicle-screen.js` (the Vehicles screen), `vehicle-card.js` (the vehicle card's "Right part" step), `item-screen.js` (the Items screen, its docked card and fit), `item-card.js` (the item card), `course-card.js` (the course card's Name and Icons steps), `add-mod.js`, `data-and-conflicts.js` (loading mods and settings, conflict cards),
`settings-registry.js` (every setting, defined once, drawn by Settings and Setup alike), `settings-panels.js` (the UI setup card, the data-folder confirmation), `menu-icons-text.js` / `menu-look.js` (the base-file copy and the
Menu Look cards), `flow.js` (step bar, Commit, Copy to Switch), `setup-wizard.js`, `tooltips.js`.

## Folder naming: nested by item, not flat "item - mod name"

Every download (both `mods/downloads/` and `mods/extracted/`) is organized
as `<category>/<item>/<mod name>`, e.g. `extracted/characters/Waluigi/Donald
Trump/romfs/...`, rather than the old flat `extracted/characters/Waluigi -
Donald Trump/`. This matters most for an item with several separate mods
(several Waluigi skins, say) - they now sit together under one `Waluigi/`
folder instead of as a wall of similarly-prefixed sibling folders, making it
much faster to find everything for one character/course by eye in Explorer.

Existing downloads from before this change are migrated automatically, in
place, the first time the app starts (or the master directory is switched) -
`Api._migrate_flat_mod_folders()` in `mod_manager.py`. It's driven primarily
by `gamebanana-mods.json`, which already knows exactly which item and mod
each downloaded archive/extracted folder belongs to, and only falls back to
guessing from a folder's name (matched against an exact `"<item> - "` prefix
from the roster) for anything not tracked there - a mod placed by hand,
outside the GameBanana flow. It's safe to re-run (every subsequent launch
does run it again) - once a folder is nested, its path no longer matches the
old flat shape, so there's nothing left for it to do.
